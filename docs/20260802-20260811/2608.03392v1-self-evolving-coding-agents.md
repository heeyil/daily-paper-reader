## 摘要
大语言模型越来越多地嵌入软件工程工作流中，作为能够检查代码库、调用工具、执行测试、调试失败并生成补丁的编码代理。然而，即使软件开发是一个动态的、反馈丰富的过程，其中代码库会演化、依赖会变化、测试会失败、修复尝试会留下可复用的经验，大多数现有代理在部署后仍然基本保持静态。这种张力推动了对自我进化的编码代理日益增长的研究工作，其中代理通过从先前的编码交互中更新其框架、记忆、技能、工具、模型或协作结构来改进其未来行为。在本综述中，我们对该新兴领域进行了系统性的综合。我们首先定义自我进化的编码代理，并将其与常规编码代理和通用自我进化代理区分开来。然后，我们开发了一个以对象为中心的分类法来刻画这些系统中进化的内容，并辅以两个正交视角：进化何时发生以及哪些软件特定的证据驱动进化。在文献中，我们发现可执行反馈、代码库级上下文和编码轨迹使软件工程作为代理自我进化的自然领域具有独特作用，但也引入了反馈可靠性、基准过拟合、安全性、可维护性、成本和泛化方面的新挑战。通过围绕这些维度组织现有工作，本综述旨在澄清自我进化编码代理的概念边界，并为设计更自适应、可靠且具有软件意识的代理系统奠定基础。我们收集的论文可在 https://github.com/zhouhao1024/Awesome-Self-Evolving-Coding-Agents 找到。

## Abstract
Large language models are increasingly embedded in software engineering workflows as coding agents that can inspect repositories, invoke tools, execute tests, debug failures, and generate patches. Yet most existing agents remain largely static after deployment, even though software development is a dynamic, feedback-rich process in which repositories evolve, dependencies change, tests fail, and repair attempts leave reusable experience. This tension has motivated a growing body of work on self-evolving coding agents, where the agent improves its future behavior by updating its framework, memory, skills, tools, models, or collaboration structures from prior coding interactions. In this survey, we provide a systematic synthesis of this emerging area. We first define self-evolving coding agents and distinguish them from conventional coding agents and general self-evolving agents. We then develop an object-centered taxonomy that characterizes what evolves in these systems, and complement it with two orthogonal perspectives: when evolution occurs and what software-specific evidence drives it. Across the literature, we find that executable feedback, repository-level context, and coding trajectories give software engineering a distinctive role as a natural domain for agent self-evolution, but also introduce new challenges in feedback reliability, benchmark overfitting, safety, maintainability, cost, and generalization. By organizing existing work around these dimensions, this survey aims to clarify the conceptual boundaries of self-evolving coding agents and provide a foundation for designing more adaptive, reliable, and software-aware agentic systems. The papers we collect can be found at https://github.com/zhouhao1024/Awesome-Self-Evolving-Coding-Agents.

## 1. 核心问题与整体含义

- **研究动机**：大语言模型（LLM）驱动的编码代理（coding agent）已能执行仓库检查、工具调用、测试执行、故障调试和补丁生成等任务。然而，大多数现有编码代理在部署后保持静态：基座模型、提示词、工具接口、记忆机制和控制流程几乎固定不变。这与其所处的软件工程环境本质矛盾——软件开发是动态、反馈密集的过程：代码库持续演化、依赖不断变化、测试会失败、修复尝试会留下可复用经验。静态代理无法从先前的编码交互中积累经验，可能在跨任务中重复同样的错误，也难以适应项目特定上下文。
- **核心问题**：如何定义并系统化理解“自我进化的编码代理”（self-evolving coding agents）？具体回答三个研究问题：
  - **RQ1**：编码代理的哪些组件会进化？通过什么机制进化？
  - **RQ2**：进化何时发生？哪些软件特有的证据驱动这一过程？
  - **RQ3**：如何在软件工程性能、可靠性及超出进化场景的泛化方面评估这类代理？
- **整体含义**：软件工程凭借可执行反馈、仓库级上下文和编码轨迹，是研究代理自我进化的天然领域；但同时也引入反馈可靠性、基准过拟合、安全性、可维护性、成本和泛化等新挑战。该综述旨在澄清概念边界，为设计更自适应、可靠、具备软件意识的代理系统建立基础。

## 2. 方法论

### 2.1 概念界定

- 区分三类系统：
  - **编码代理（Coding Agents）**：在软件工程环境中行动，与仓库、工具、测试和人类开发者交互，而非仅做孤立文本生成。
  - **通用自我进化代理（General Self-Evolving Agents）**：基于自身执行轨迹、环境反馈和积累经验，修改行为或内部组件（提示、记忆、工具、策略、架构）。
  - **自我进化编码代理（Self-Evolving Coding Agents）**：位于两者交叉点，特指基于先前编码尝试和软件特定反馈来更新自身行为或内部组件的智能体软件工程系统。其独特性在于进化发生在软件工程回路中：反馈来自可执行构件（单元测试、编译器诊断、运行时跟踪、静态分析警告、CI 日志、代码审查）而非仅文本批评或标量奖励。

### 2.2 核心分类法：以进化对象为中心（object-centered taxonomy）

论文将现有工作分为五大类：

1. **Agent 框架自我进化（Agent Framework Self-Evolution）**
   - 将代理自身视为可修改的软件工件，直接改写自身脚手架代码。
   - 代表机制：脚手架重写（SICA、SIFT、STOP）、基于存档的框架进化（Darwin Gödel Machine、Mendel GM、Huxley GM）。
   - 反馈循环具体：编译错误、单元测试、shell 输出、基准结果直接验证修改是否有效。

2. **记忆自我进化（Memory Self-Evolution）**
   - 持续构建、精炼和复用显式记忆组件，记录软件特定经验（问题解决轨迹、仓库历史、失败/成功补丁、测试结果、漏洞模式）。
   - 三种形式：经验记忆（SWE-Exp、EvoCoder、EvoRepair、Subtask-Level Memory）、仓库记忆（Repository Memory）、计划抽象记忆（SAGE）。
   - 关键挑战：选择性进化，避免噪声日志、误导性测试和脆弱补丁污染记忆。

3. **技能与工具自我进化（Skill and Tool Self-Evolution）**
   - 将软件工程经验转化为可复用的操作能力（过程性知识）。
   - 代表方向：轨迹提炼技能（CODESKILL，任务级 + 事件驱动技能）、仓库特定技能（GSkill）、轨迹派生技能注册表（Socratic-SWE）、代码效率优化技能（EffiSkill）、在线工具创建与修订（Live-SWE-Agent）。
   - 核心特点：强调“可操作性”——代理不仅要记住失败，还要获得避免类似失败的流程。

4. **模型自我进化（Model Self-Evolution）**
   - 改变模型侧组件：基座模型、适配器、代理策略、奖励模型或验证器。
   - 关键边界：普通后训练只有在其训练信号闭环于代理自身尝试时才构成自我进化。
   - 代表方向：自博弈策略进化（Self-play SWE-RL、Agent-RLVR）、编码器-验证器共同进化（ReVeal、CURE、ZeroCoder、Sol-Ver）、对抗测试进化（ACE）。
   - 风险：自生成数据不等于进化，需要跨迭代的可学习信息增益。

5. **工作流与拓扑自我进化（Workflow and Topology Self-Evolution）**
   - 让工作流、代理角色和通信拓扑随任务难度、执行反馈和验证需求自适应。
   - 代表方向：多代理拓扑（SEMAG、EvoMAC、AgentConductor）、工作流图（SEW、AFlow、EvoAgentX）。
   - 核心洞见：协作应被视为软件工程决策——不仅决定写什么代码，还要决定哪些角色应检查、测试、批评或修订代码。

### 2.3 两个正交视角

- **进化时机（Evolving Time）**：
  - **任务内进化（Task-time）**：解决当前编码任务过程中即时调整（如 Live-SWE-Agent 边解题边创建工具、SEMAG/AgentConductor 根据任务难度自适应多代理工作流）。
  - **任务后进化（Post-task）**：一个任务结束后，将完整轨迹抽象为经验、技能、仓库知识，供后续任务复用。
  - **阶段式进化（Stage-wise）**：大量软件交互积累后更新代理（如自博弈 SWE-RL、Agent-RLVR）；最接近跨代理世代的自我改进，但需严格区分于普通 SWE 后训练。

- **进化证据（Evolving Evidence）**：
  - **结果证据（Outcome Evidence）**：基准解决率、测试通过率、验证器分数等粗粒度选择压力，用于筛选代理变体、工作流、策略；优势是可比较，劣势是不解释原因。
  - **环境反馈（Environmental Feedback）**：命令输出、编译器诊断、运行时异常、测试日志等局部反馈，支撑任务内适应、工具创建和调试导向进化。
  - **轨迹派生证据（Trajectory-Derived Evidence）**：完整代理尝试记录，揭示尝试如何展开；最常用于构建记忆和技能。

## 6. 主要结论与发现

1. **自我进化是谱系而非单一技术**：从轻量反射和记忆，到工具/工作流修改，再到策略和架构演化，构成连续谱系。软件工程是这一谱系的理想测试场。
2. **软件工程特有证据至关重要**：可执行反馈（测试、编译、CI）、仓库级上下文和编码轨迹是区别于通用自我进化代理的关键信号源，使进化有具体、可验证的锚点。
3. **进化时机与证据类型紧密耦合**：编译器错误可即时修正当前补丁，跨问题重复失败应固化为记忆/技能，大量交互才能驱动模型级更新。
4. **每种进化对象都有独特风险**：框架进化有过拟合基准危险；记忆进化需防噪声污染；技能进化需平衡通用性与具体性；模型进化可能因弱验证器导致奖励黑客；工作流/拓扑进化可能带来过度协调成本。
5. **评估必须超越一次性任务成功**：需覆盖长期可维护性、安全性、鲁棒性、成本以及超出进化场景的泛化。
6. **“自我进化”定义严格性**：阶段式进化必须是闭环于代理自身尝试的信号，而非任何 SWE 定向后训练；当前许多工作（如 SWE-Gym、R2E-Gym、SWE-RM）应定位为进化基础或支撑证据，而非自我进化代理本身。
