## 摘要
没有任何单一的大语言模型（LLM）能在所有查询和预算约束下表现最优，因此模型路由对于经济高效的部署至关重要。现有的路由器采用不同的公式和实现方式，使得公平比较和扩展变得困难。我们提出了一种统一的LLM路由公式，将其视为一个顺序决策过程，包含五个组成部分：上下文编码器、模型编码器、评分函数、决策规则和学习信号，涵盖单轮、多轮和个性化路由。基于这一公式，我们开发了一个自动化流水线，用于构建路由监督，并在响应质量和推理成本上联合评估路由器。由此产生的基准测试xRouteBench涵盖了通用LLM、记忆增强、视觉、时间序列和个性化路由任务。我们进一步推出了LLMRouter，一个包含16个以上代表性路由器的开源模块化基础设施。我们的实证研究表明，学习型路由器相对地超过最强的固定模型基线14.6%，轻量级路由器在严格的成本约束下更具竞争力，以及用户条件路由持续提高个性化。

## Abstract
No single large language model (LLM) is optimal across all queries and budget constraints, making model routing essential for cost-effective deployment. Existing routers adopt diverse formulations and implementations, making fair comparison and extension difficult. We present a unified formulation of LLM routing as a sequential decision process characterized by five components: context encoders, model encoders, scoring functions, decision rules, and learning signals, covering single-turn, multi-turn, and personalized routing. Based on this formulation, we develop an automated pipeline for constructing routing supervision and evaluating routers jointly on response quality and inference cost. The resulting benchmark, xRouteBench, spans generic LLM, memory-augmented, vision, time-series, and personalized routing tasks. We further introduce LLMRouter, an open-source modular infrastructure with more than 16 representative routers. Our empirical study shows that learned routers outperform the strongest fixed-model baseline by 14.6% relatively, lightweight routers become more competitive under tight cost constraints, and user-conditioned routing consistently improves personalization.

## 1. 核心问题与整体含义（研究动机和背景）

- 随着 LLM 生态的迅速扩展，不同模型在性能、成本和任务能力上差异巨大，**没有任何单一模型能在所有查询和预算约束下同时最优**。因此，模型路由（LLM Routing）成为在保证响应质量的同时降低推理成本的关键手段。
- 现有 LLM 路由方法（二元路由器、成本感知级联、基于图的路由器、个性化路由器、基于强化学习的智能体路由器等）在**问题定义、形式化体系、代码实现、训练监督方式和候选模型池配置**上各不相同，导致：
  - 难以公平对比不同方法，无法区分性能差异来自路由器本身还是实验设置；
  - 无法复用和扩展，新任务 / 新候选池需要重新搭建整套工程；
  - 缺乏统一的、成本感知的标准评估框架，多轮路由和个性化路由尤其缺少标准化评估基准。
- 论文的核心目标是构建一套**统一基础设施**，使得路由器的开发、评估和部署具备标准化、模块化和可复现性，并在此基础上系统性地对比多类路由方法。

## 2. 方法论

### 2.1 统一形式化：路由作为顺序决策过程

- 将 LLM 路由建模为顺序决策问题：
  - 状态 `s = (q, u, h_t)`：包括输入查询 `q`、可选用户上下文 `u`、交互历史 `h_t`；
  - 动作 `a ∈ M ∪ {K}`：选择候选模型 `m`（调用后返回响应并更新历史）或终止动作 `K`（聚合所有响应输出最终答案）；
  - 优化目标：
    \[
    \pi^* = \arg\max_\pi \mathbb{E}_{q, \tau \sim \pi} [ \mathrm{perf}(y|q) - \lambda \cdot c(\tau) ]
    \]
    其中 `perf` 为任务质量指标，`c(τ)` 为轨迹成本，`λ` 控制质量与成本的权衡。

- 一个路由器的完整设计由**五类组件**刻画：
  1. **上下文编码器 E_q**：将路由状态映射为嵌入向量或文本表示；
  2. **模型编码器 E_m**：编码候选模型，可用静态元数据、历史表现档案、学习得到的嵌入或文字描述；
  3. **评分函数 g**：计算状态与候选模型的匹配分数；
  4. **决策规则 d**：将分数转化为具体动作（贪婪 argmax / 成本感知阈值 / 终止判断等）；
  5. **学习信号 L**：点级标签、成对偏好或轨迹级奖励，用于拟合上述组件。

- 基于状态中观测到的部分，现有路由器分为三类：
  - **单轮路由**：状态只有查询 `q`；
  - **多轮路由**：状态包含交互历史 `h_t`（含智能体式分解与聚合）；
  - **个性化路由**：状态额外包含用户上下文 `u`。

### 2.2 自动化评估与数据构建流水线

- 路由器评估需要知道每个候选模型在每个查询上的响应质量与成本，传统做法是手工为固定池和固定 benchmark 构建数据，难以扩展。
- LLMRouter 提供**三段式自动化流水线**：
  1. **查询整理（Query Curation）**：从源基准采样、归一化、划分训练 / 测试；
  2. **响应收集（Response Collection）**：将每个查询发送给声明在配置文件中的全部候选模型，记录响应与 token 数；
  3. **指标评分与定价（Metric Scoring & Pricing）**：用任务原生指标评分，按 token 数计算成本。
- 最终形成稠密的 **查询–模型性能 / 成本矩阵**，既作为训练监督，也作为统一测试平台。评估时每个测试查询只调用路由器选择的模型，因此所有路由器面对同一查询、同一候选池、同一指标，差异只来自路由策略本身。

## 3. 实验设计

### 3.1 基准：xRouteBench

- 覆盖 5 个类别、8 个测试集，共 **4,767 个测试查询**：
  - **通用 LLM 任务**：知识问答（MMLU、MMLU-Pro、ARC-Challenge、OpenBookQA、CommonsenseQA、BoolQ、HellaSwag、SQuAD）、数学推理（GSM8K、MATH、AIME）、代码生成（MBPP、HumanEval），共 3,729 条；
  - **记忆增强任务**（长对话记忆）：LoCoMo（314 条）、LongMemEval（101 条），使用 token 级 F1；
  - **时间序列任务**：TSRBench（127 条，多选准确率），每个序列同时渲染为文本和图像描述；
  - **视觉任务**：图像数学推理（Geometry3K 61 条、MathVista 100 条）和视频理解（Charades-Ego 27 条）；
  - **个性化任务**：Chatbot Arena / MT-Bench 对话偏好（308 条），由 persona 条件 LLM 裁判打分。

### 3.2 候选模型池

- 18 个开源模型，参数从 7B 到 671B，通过 Together API 和 NVIDIA NIM API 提供，如 Gemma-2-9B、Mistral-7B、Mixtral-8x22B、Qwen2.5-7B、Qwen3-Next-80B、Llama-3.3-70B、GPT-OSS-20B/120B、DeepSeek-V3.1、Cogito-v2 等。输入价格跨度约 25 倍（$0.05–$1.25 / 1M tokens）。

### 3.3 对比的 Router

- LLMRouter 实现了 **16+ 种路由器**：
  - 规则基线：Smallest-LLM、Largest-LLM；
  - 单轮：kNNRouter、SVMRouter、MLPRouter、MFRouter、EloRouter、RouterDC、Hybrid LLM、AutoMix、GraphRouter、CausalLM；
  - 多轮：Router-R1、kNN-MultiRound、LLM-MultiRound；
  - 个性化：GMTRouter、PersonalizedRouter。

### 3.4 评估协议

- 加权奖励：`α·perf − β·cost`，扫描 5 组权重（从纯质量 (1.0, 0.0) 到重成本 (0.2, 0.8)）；

- 个性化任务使用 persona 条件 LLM 裁判（DeepSeek-V3.1），三种结果 win/tie/loss 记为 1/0.5/0；
- 额外进行了真实用户（Slack）偏好收集与多智能体系统路由实验。

## 6. 主要结论与发现

1. **没有任何单一路由器在所有任务中占优**：不同任务和成本约束下的最优路由器不同；平均性能高反映的是稳定性，而非单一场景下的绝对优势。
2. **学习型路由显著优于最强固定模型基线**：总是选择最大模型成本最高但质量平庸；学习型路由器能为许多最大模型也回答错误的查询选择更小更便宜的模型，相对性能提升 14.6%。
3. **多轮路由并不一致优于单轮路由**：分解与聚合引入额外成本和冗余信息，且性能高度依赖执行分解/聚合的基础模型（Qwen2.5-3B-Instruct）能力。
4. **个性化路由有效，但用户建模方式至关重要**：GMTRouter 在 persona 裁判下最好（68.78）；但在真实用户数据上 PersonalizedRouter 最好（83.05），GMTRouter 跌至第六——模拟设置与真实偏好不完全一致。
5. **路由排名随成本权重变化剧烈**：RouterDC 在纯质量下第一、重成本下垫底；MLPRouter 在视觉任务质量优先时靠后，但在 β≥0.4 时成为最优——应依据部署需求选择匹配的成本–质量工作点。
6. **多智能体系统中对每个节点独立路由能带来收益**：7 个学习路由器中 6 个平均性能超过 Largest-LLM（最佳 MFRouter 76.48 vs 71.48）。

## 7. 优点

- **统一形式化**：将单轮、多轮、个性化路由统一为顺序决策过程，便于理解和对比。
- **模块化基础设施**：新增路由器只需实现 `route_single` 和 `loss_func`，数据构建、训练、评估、部署全部复用，切换配置即可。
- **自动化流水线**：降低构建新任务/新候选池路由监督的成本，提升可复现性。
- **多场景基准**：xRouteBench 覆盖长文本、视觉、视频、时间序列、个性化等此前被忽略的领域，并统一采取成本感知评估协议。
- **工程实用性**：支持 OpenAI 兼容服务器、OpenClaw 部署到 Slack/Discord、ComfyUI 可视化无代码接口，还支持多智能体场景，架起了离线研究与真实应用之间的桥梁。
- **真实用户验证**：提供了真实用户偏好数据与模拟 persona 的对比，揭示了真实部署中的排名不一致问题，具有实践参考价值。

## 8. 不足与局限

- **算力与成本细节缺失**：未报告训练和推理的总计算量（GPU 时数、API 预算），难以评估方法复现成本。
- **候选池依赖**：所有结论基于特定 18 模型池与两家 API 提供商，结果可能随池变化而不能完全迁移。
- **多轮路由评估不充分**：仅用单一弱基础模型（3B）执行分解聚合，且 RL 路由器（Router-R1）在性能优先设置下表现明显偏弱（35.64，远差于单轮），可能低估了多轮/智能体式路由的潜力。
- **实验统计严谨性不足**：未报告多次运行的标准差或显著性检验；部分测试集样本极少（Video 27 条、AIME 13 条、HumanEval 16 条），容易产生偶然性结果。
- **个性化评估的偏差风险**：persona 裁判基于生成 persona 模拟用户偏好，不能完全代表真实用户的多样性；真实用户数据仅来自 15 位 Slack 用户，规模小且有自选择偏差。
- **部署评估范围有限**：真实用户测试仅覆盖聊天场景，未覆盖长上下文、视觉等其余轨道的线上表现。
- **开放权重限制**：候选池全部是开放权重模型，未覆盖闭源商业模型（如 GPT-4o、Claude），实际部署中的池差异可能影响路由选择。
