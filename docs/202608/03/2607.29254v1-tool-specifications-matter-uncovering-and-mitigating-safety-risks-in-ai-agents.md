## 摘要
AI代理将大型语言模型（LLMs）与外部工具相结合，使其能够执行复杂任务，并将模型输出转化为现实世界中的实际行为。然而，当LLMs作为代理部署时，其安全性往往大幅下降，但这种退化的根源仍鲜为人知。在本文中，我们确定模式化格式的工具规范是代理安全性退化的主要原因，并通过白盒表示分析表明，它们削弱了模型内部的拒绝信号，并导致不安全的工具执行。基于这一发现，我们提出SafeKeep，一种推理时的安全防护机制，将安全判断与工具执行解耦：它使用扁平化的文本工具规范来评估请求，同时保留原始模式化格式的规范用于执行。在两个代表性基准测试和四个LLM（包括白盒和黑盒模型）上，SafeKeep将有害请求的平均拒绝率从23.8%提高到70.6%，并将观察级提示注入下的平均攻击成功率从25.6%降低到2.5%。它还优于现有的防护措施，并保留了任务处理能力。我们在https://github.com/snowcatsmoking/SafeKeep 发布了代码和数据。

## Abstract
AI agents extend large language models (LLMs) with external tools, enabling them to perform complex tasks and translate model outputs into consequential real-world actions. Yet LLMs often become substantially less safe when deployed as agents, and the source of this degradation remains poorly understood. In this paper, we identify schema-formatted tool specifications as a primary source of agent safety degradation and show, through white-box representation analysis, that they weaken the model's internal refusal signals and contribute to unsafe tool execution. Building on this finding, we propose SafeKeep, an inference-time safeguard that decouples safety judgment from tool execution: it assesses requests using flattened textual tool specifications while retaining the original schema-formatted specifications for execution. Across two representative benchmarks and four LLMs, including both white-box and black-box models, SafeKeep increases the average refusal rate for harmful requests from 23.8% to 70.6% and reduces the average attack success rate under observation-level prompt injection from 25.6% to 2.5%. It also outperforms existing safeguards and preserves task-handling capability. We release the code and data at https://github.com/snowcatsmoking/SafeKeep .

## 1. 核心问题与整体含义（研究动机和背景）

- **研究现象**：相同的大语言模型（LLM）在普通聊天场景下会拒绝有害请求，但当其被部署为 AI 代理（Agent）时，可能转而执行这些有害请求。已有研究（AgentHarm、InjecAgent 等）证实了这一安全退化（safety degradation）现象，但其根源尚未被厘清。
- **核心问题**：为什么相同的 LLM 在聊天环境下具有良好的抗拒有害请求能力，一旦作为代理部署就变得不可靠？这一问题的答案是构建安全代理的前提。
- **关键发现**：论文通过白盒表示分析，首次定位到 **Schema 格式化的工具规范（schema-formatted tool specifications）** 是导致代理安全退化的主要来源。其机制是：Schema 格式会诱导模型的隐藏状态向一个与"拒绝方向"（refusal direction）相反的方向偏移，削弱了模型内部的拒绝信号，从而促使不安全工具执行。
- **整体含义**：工具规范不仅是功能接口，更是影响模型安全行为的关键输入因素。该工作为代理安全提供了一种轻量级、模型无关的推理时防护范式。

## 2. 方法论：核心思想、关键技术细节与算法流程

### 2.1 核心思想
- **SafeKeep 的总体思路**：将"安全判断"与"工具执行"解耦。
  - 安全判断阶段：使用**扁平化文本（flattened textual）**形式的工具规范来评估请求，因为这种表示不会触发 Schema 格式带来的"拒绝抑制"效应。
  - 工具执行阶段：保留**原始 Schema 格式**的工具规范，确保代理原有的工具选择与执行接口不变。
- **核心逻辑**：安全评估和工具执行使用不同的规范表示，从而在保证安全性的同时不牺牲任务处理能力。

### 2.2 关键技术细节

**① 机制分析部分**

- **Refusal Direction（拒绝方向）提取**：遵循 Arditi et al. (2024) 的方法，将有害与良性请求的最终 token 隐藏状态均值之差作为拒绝方向，投影后的值作为拒绝分数。公式为：$s = h_g^\top \hat{r}_f$，其中 $\hat{r}_f = r_f / \|r_f\|$。
- **Schema Direction（模式方向）定义**：同一工具规范在 Schema 格式与扁平化文本格式下产生的隐藏状态差值的均值，按有害/良性请求类别分别提取，公式为：
  - $R_c^{(\ell)} = \mathbb{E}_{x \sim D_c}\left[h_{schema}^{(\ell)}(x) - h_{text}^{(\ell)}(x)\right]$，$c \in \{harmful, benign\}$
- **层间余弦相似度分析**：计算每层中 Schema Direction 与拒绝方向的余弦相似度，并对照随机方向的基线分布，发现有害请求的 Schema Direction 在所有层都与拒绝方向呈现负对齐。
- **第一生成 Token 投影分析**：在解码开始后，将第一个生成 token 的隐藏状态投影到拒绝方向，发现 Schema 格式显著减小了有害/良性请求的分离度。
- **激活引导验证（因果验证）**：在峰值拒绝层 $\ell^*$ 处减去单位归一化的有害 Schema Direction：
  - $\tilde{h}^{(\ell^*)} = h^{(\ell^*)} - \alpha \hat{R}_{harmful}^{(\ell^*)}$
  - 通过变化干预强度 $\alpha$（0 到 12）验证了该方向与不安全行为之间的因果关系。

**② SafeKeep 方法**

- **Safety Judgment（安全判断）阶段**：
  - 构造"安全评估上下文"：安全评估者角色描述 + 原始代理角色和工具使用说明 + **扁平化文本工具规范** + 待评估请求。
  - 扁平化转换方法：去除 JSON 语法、保留工具名、功能签名、参数语义等语义信息。
  - 模型输出 YES/NO 判断是否安全执行该请求。
- **Execution Control（执行控制）阶段**：
  - NO → 将请求转发至原始代理流水线，Schema 工具规范原样保留用于执行。
  - YES → 阻断工具使用，预填充简短拒绝前缀（如 "I'm sorry, but I can't help with that."），引导模型生成具体拒绝回复。
- **模型无关性**：不需要参数更新，不需要访问模型激活值，可用于开源模型和专有 API 模型。

## 6. 主要结论与发现

1. **Agent 安全退化伴随内部表示退化**：从聊天到代理场景，有害-良性请求在拒绝方向上的分离度（AUROC）从 0.927 降至 0.740（Llama），行为拒绝率从 58% 降至 3%。
2. **工具规范是退化的主导来源**：在代理上下文的三个组件中，工具规范的加入造成的 AUROC 下降最大（平均 -0.136），且上下文长度不能解释该退化。
3. **表示形式比语义内容更关键**：将 Schema 格式转换为扁平化文本后，AUROC 显著回升（0.740 → 0.885）；而保留 Schema 格式仅随机化语义内容则几乎无改善（0.776）。
4. **机制层面**：Schema 格式在预填充阶段诱导出与拒绝方向负对齐的隐藏状态方向；在生成阶段显著压缩有害/良性请求在拒绝方向上的分离；通过激活引导实验证明该方向因果性地贡献于有害工具执行。
5. **SafeKeep 有效提升安全性**：在四个 LLM 上，有害请求拒绝率从 23.8% 平均提升到 70.6%；提示注入攻击成功率从 25.6% 降至 2.5%。
6. **SafeKeep 保持任务处理能力**：AgentHarm 准确率从 60.9% 提升到 79.6%（因拒绝率提升带动的分类正确）；InjecAgent 的 Valid-B/Valid-E 均高于基线。
7. **扁平化表示是安全判断的关键**：SafeJudge（保留 Schema 格式）的拒绝率（45.0%）和 ASR（19.1%/22.2%）均显著差于 SafeKeep（70.6%，2.3%/2.7%）。

## 7. 优点

- **定位精准**：首次将安全退化机制性地归因于工具规范的"表示形式"而非"语义内容"，并通过双维度消融严格区分了二者。
- **机制解释深入**：从预填充阶段的 Schema Direction 负对齐、生成阶段的表示分离压缩到激活引导的因果验证，形成了完整的机制链条。
- **方法轻量实用**：SafeKeep 不需要微调、不需要访问内部激活、不需要修改代理或工具接口，适用于任何 LLM 后端，部署门槛低。
- **设计优雅**：安全判断与工具执行在表示层面解耦，既规避了 Schema 格式的"执行暗示"效应，又保留了代理原有的工具调用功能。
- **基准设计严谨**：配对数据集的构建（最小化改写、人工审查、7:3 划分）尽可能避免了方向提取中的混淆因素。
- **评估覆盖全面**：同时覆盖直接有害请求和间接提示注入，同时评估安全性和任务处理能力，避免以牺牲功能为代价换取安全的偏差。

## 8. 不足与局限

- **实验局限**：
  - 因果验证（激活引导实验）仅在 Llama3.1-8B-Instruct 上进行，其他模型的机制一致性未验证。
  - 未覆盖更大规模模型（如 70B+）或更多模型家族（如 Claude、DeepSeek）下的表现。
  - 未在真实代理环境（如多步工具调用、动态工具集、工具输出反馈循环）中进行端到端评估。
- **方法局限**：
  - 引入了额外的一次 LLM 推理调用，带来推理延迟和 API 成本开销，论文未量化该开销。
  - 安全判断阶段仍依赖 LLM 自身的判断能力，对高度复杂或隐蔽的恶意请求可能存在误判风险。
  - YES/NO 二元判断可能忽略部分场景下"可安全执行部分操作"的中间状态，灵活性有限。
  - 扁平化转换是针对 JSON Schema 设计的，对其他工具规范格式（如 OpenAPI、GraphQL schema）的适配性未验证。
- **数据局限**：
  - 配对数据集通过 Claude 改写生成，可能在改写过程中引入非预期差异；改写质量虽经人工审查，但审查主观性不可避免。
  - ToolSafety 和 AgentHarm 中的工具场景有限，对长尾/领域特定工具规范的代表性不足。
- **偏差风险**：
  - 所有评估均基于英文数据，未测试多语言场景下的安全判断能力。
  - 对良性请求存在潜在误拒风险（论文未报告良性请求误拒的具体数据），特别是在安全阈值偏保守的情况下，可能影响用户体验。
