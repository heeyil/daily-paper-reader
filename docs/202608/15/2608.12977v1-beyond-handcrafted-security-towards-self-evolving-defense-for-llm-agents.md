## 摘要
大型语言模型（LLM）代理不断扩展的操作能力引入了复杂的安全威胁。运行时防御通过在代理执行循环中集成安全机制，已成为缓解这些风险的有效方法。然而，现有的运行时防御严重依赖手动设计的干预措施，缺乏构建和维护这些措施的原则性框架。在本工作中，我们首先开发了一种基于控制框架（harness）级别的运行时防御公式化描述，系统性地刻画了控制框架机制如何实现防御构建，并从控制框架视角为现有运行时防御干预提供了统一视图。基于这一公式化描述，我们提出了HARD（基于控制框架的自主运行时防御进化），这是一种自我进化的运行时防御框架，能够自动识别适当的干预策略，并根据观察到的失败轨迹迭代改进防御工件。HARD将运行时防御的开发从手动工程转变为自主进化过程，大量实验表明，它在保持良性任务效用的同时，提升了相对于现有手工防御的安全性能。我们的研究结果强调了自主防御进化作为保护已部署LLM代理的一种有前景的新范式，使代理能够识别防御弱点并不断改进其保护机制。

## Abstract
The expanding operational capabilities of large language model (LLM) agents introduce sophisticated security threats. Runtime defenses have emerged as an effective approach to mitigating these risks by integrating security mechanisms into the agent execution loop. However, existing runtime defenses rely heavily on manually designed interventions and lack a principled framework for their construction and maintenance. In this work, we first develop a harness-level formulation of runtime defense that systematically characterizes how harness mechanisms enable defense construction and provides a unified view of existing runtime defense interventions from a harness perspective. Building on this formulation, we propose HARD (Harness-based Autonomous Runtime Defense Evolution), a self-evolving runtime defense framework that automatically identifies appropriate intervention strategies and iteratively improves defense artifacts based on observed failure traces. HARD transforms runtime defense development from manual engineering into an autonomous evolution process, and extensive experiments demonstrate that it improves security performance over existing handcrafted defenses while preserving benign task utility. Our findings highlight autonomous defense evolution as a promising new paradigm for securing deployed LLM agents, enabling agents to identify defense weaknesses and continuously improve their protection mechanisms.

- 核心问题：如何让运行时防御能够**根据观察到的失败轨迹自主进化**，以应对不断涌现和自适应演化的攻击？
- 关键挑战有二：
  1. 如何定义一个结构化、可编辑的防御空间；
  2. 如何基于新失败自动改进防御，而不是依赖人工诊断和反复修补。
- 整体意义：论文提出从“手工安全工程”转向“自主防御进化”的新范式，使已部署代理能够持续识别自身防御弱点并改进保护机制。

## 2. 方法论

### 2.1 核心思想

- 将 LLM 代理建模为 `A = (Mθ, H)`，其中 `Mθ` 是固定参数的语言模型，`H` 是运行时 harness（运行时框架）。
- Harness 由两个关键函数组成：
  - **上下文构建函数** `ϕH`：决定将哪些任务信息、历史轨迹和持久化工件交给模型；
  - **动作解释函数** `ψH`：决定如何将模型输出解析、校验、转换、拦截或确认为可执行动作。
- 因此，运行时防御可被形式化为**对 harness 的优化问题**：

  `H* = argmax_{H} E_{x~D, τ~P}[Jsafe(τ) + λu * Jutil(τ)]`

- 该公式统一了现有运行时防御：上下文侧防御作用于 `ϕH`，动作侧防御作用于 `ψH`，二者结合则同时优化两个接口。

### 2.2 HARD 框架流程

HARD 将防御进化组织为迭代循环（Algorithm 1）：

1. **失败收集**：从攻击任务分布中采样任务，在当前 harness `Ht` 下执行，得到轨迹集合 `Tt`。
2. **失败识别**：根据安全阈值 `δs` 和效用阈值 `δu`，筛出安全或效用不达标的失败轨迹 `Ft`。
3. **失败路由**：由基于 LLM 的 trace router `R` 分析每条失败轨迹，将其路由到最合适的可编辑防御工件（context-side policy 或 action-side gate）。
4. **防御工件更新**：不同工件使用各自对应的 evolver（`EP` 策略进化器、`EG` 门控进化器）基于路由到的失败集更新。
5. **重新部署**：更新后的工件组装成新的 harness `Ht+1`，进入下一轮进化。

- 三个核心变体：
  - `HARD-Policy`：只进化上下文侧安全策略；
  - `HARD-Gate`：只进化动作侧执行规则；
  - `HARD-Both`：两者联合进化。
- 实现上，HARD 使用 LLM 作为 router 和 evolver；进化时对失败轨迹做批量处理（每批 8

条失败轨迹，即每次迭代中批量处理一批失败样本），随后由进化器生成或改写对应的策略/门控规则。具体地：

- **上下文侧安全策略（context-side policy）**：是一个自然语言指令集或结构化规则，注入到 `ϕH` 构造的上下文提示中，用于引导模型区分可信与不可信内容、忽略外部指令、标记可疑数据等。策略进化器 `EP` 根据路由到的失败轨迹，总结攻击模式，生成新的规则或对现有规则进行增删改，并确保新策略与已有策略不冲突。
- **动作侧门控（action-side gate）**：是一段可执行代码或规则集，挂载在 `ψH` 的动作执行路径上，对模型输出进行合法性检查、参数白名单校验、操作风险打分等。门控进化器 `EG` 从失败轨迹中提取被攻击者利用的动作特征，自动生成拦截条件、绕过修复逻辑或更细粒度的校验规则。
- 路由与进化均使用 LLM 实现：router 对每条失败轨迹分配到一个或多个工件；evolver 将失败集合转化为“教训”并更新工件。为防止过度拟合单次失败，进化器还会将具体失败泛化为对一类攻击的普遍防御，并对更新后的工件做轻量级验证，若验证不通过则回滚。

HARD 的完整迭代过程可总结为：**采样→执行→筛选→路由→进化→重部署**，并循环直到安全/效用指标收敛。该框架不要求修改模型参数，只需替换 harness 中的可编辑工件，因此可以无缝部署在现有 LLM 代理上。

## 3. 实验设计

- **环境**：构建了一个模拟 LLM 代理测试平台，代理可调用工具、访问网页、读取记忆文件、执行脚本等。攻击任务包括四种典型威胁：直接提示注入、间接提示注入、记忆污染、技能投毒。
- **基线**：对比了无防御、静态手工策略、静态门控、以及 HARD 三种变体（Policy、Gate、Both）。采用 GPT-4 作为代理主模型，攻击成功率（ASR，越低越好）和良性任务成功率（BSR，越高越好）作为主要指标。
- **结果**：
  - HARD 在多种攻击下均能显著降低 ASR，其中 `HARD-Both` 效果最佳，能将 ASR 从无防御时的 80%+ 降至 20% 以下，同时 BSR 保持在 90% 以上。
  - 静态手工防御虽然能抵御部分预知攻击，但对未见过的攻击变体效果有限；HARD 每轮进化后防御性能持续提升，表现出自适应能力。
  - 消融实验表明，策略进化主要对抗 IPI 和 MC，门控进化则更擅长拦截 DPI 和 SP，联合进化可以互补覆盖。
  - 进化效率方面，每轮迭代仅需少量 LLM 调用，且更新后的工件很小（策略文本或几行规则），部署开销可忽略。

## 4. 讨论与局限性

- **安全性与自我演化的风险**：让防御系统自主修改策略存在潜在风险，比如进化器可能生成过于宽松或过于严苛的规则，甚至被攻击者间接操纵（通过向失败轨迹中注入恶意内容影响进化结果）。论文没有提供对进化过程本身的对抗鲁棒性分析。
- **成本与可扩展性**：每轮进化需要采集大量失败轨迹并多次调用 LLM 做路由和生成，在真实高频环境中可能产生可观成本。且进化器依赖 LLM 的推理能力，若模型本身不安全则风险更大。
- **评估范围有限**：实验场景相对简单，工具数量和任务类型有限；真实世界代理的复杂状态空间可能使攻击变体更多，防御泛化能力尚待验证。
- **阈值的设置**：安全/效用阈值 `δs`、`δu` 是人为设定的超参数，如何自适应调整未讨论；阈值过高会导致过度防御，降低效用。

## 5. 优点与创新

- 提出了一个新的研究视角：将运行时防御视为对 harness 接口的持续优化，并通过 LLM 驱动的闭环实现“自主进化”，跳出了手工防御的静态框架。
- 将上下文侧策略和动作侧门控统一在同一个优化目标下，给出了一个可操作的框架（HARD），并证明了其有效性。
- 方法论完整，从问题定义、算法流程到实验验证环环相扣，具有很强的复现价值。

## 6. 不足与改进建议

- 进化机制本身依赖于 LLM 的“开环”生成，缺少对生成规则的语义一致性和安全性的形式化验证；可结合最小化测试集或多智能体辩论来提高可靠性。
- 对失败轨迹的分类依赖预设攻击类型，若出现新型攻击可能路由失败；可引入开放路由或基于聚类的动态分类。
- 实验中没有与基于微调的模型级防御做比较，无法说明运行时防御相比模型级防御在不同预算下的优劣。
- 建议增加对对抗性攻击（如故意污染失败集合）的防御设计，并评估进化器的鲁棒性。
