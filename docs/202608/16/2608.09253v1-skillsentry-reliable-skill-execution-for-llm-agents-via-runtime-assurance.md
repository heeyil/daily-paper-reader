## 摘要
LLM代理越来越多地配备技能，以通过多步推理和工具使用来执行复杂任务。尽管技能提供了可复用的程序性知识，但代理在执行时仍可能不可靠。即使代理在技能指导下已展示出完成任务的能力，由于偏离技能流程或个别步骤执行错误，它也可能无法在类似任务或重复运行中一致地完成。这种不稳定性限制了LLM代理的实际可靠性。为了解决这个问题，我们提出了SkillSentry，这是一种面向技能的运行时保障框架，基于一种新的领域特定语言（DSL）来表示技能执行的运行时指导。SkillSentry通过结合从相应技能文档中提取的技能规范与从历史成功和失败轨迹中挖掘的执行经验，来初始化运行时指导。然后，它包裹代理执行循环，以在当前指导下监控和引导技能执行，同时利用新收集的轨迹迭代优化指导。我们在两个LLM代理的15项技能上评估SkillSentry，每个代理配有两个骨干模型，即Claude Code配Claude-Haiku-4.5和Claude-Opus-4.6，以及Codex配GPT-5.2和GPT-5.4。我们的结果表明，SkillSentry使LLM代理的技能任务成功率平均提高24.1%，同时在重复运行中表现出更低的变异性。

## Abstract
LLM agents are increasingly equipped with skills to perform complex tasks through multi-step reasoning and tool use. Although skills provide reusable procedural knowledge, agents may still execute them unreliably. Even when an agent has demonstrated the capability to complete tasks under the guidance of a skill, it may fail to do so consistently across similar tasks or repeated runs due to deviations from the skill procedure or incorrect execution of individual steps. Such instability limits the practical reliability of LLM agents. To address this problem, we propose SkillSentry, a skill-oriented runtime assurance framework built upon a new domain-specific language (DSL) for representing runtime guidance for skill execution. SkillSentry initializes the runtime guidance by combining a skill specification extracted from the corresponding skill document with execution experience mined from historical successful and failed traces. It then wraps around the agent execution loop to monitor and guide skill execution under the current guidance, while iteratively refining the guidance using newly collected traces. We evaluate SkillSentry on 15 skills across two LLM agents, each paired with two backbone models, i.e., Claude Code with Claude-Haiku-4.5 and Claude-Opus-4.6, and Codex with GPT-5.2 and GPT-5.4. Our results show that SkillSentry improves the task success rate of LLM agents by 24.1% across skills, on average, while exhibiting lower variability across repeated runs.

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：大语言模型（LLM）代理通过多步推理和工具调用来执行复杂任务。为了复用任务求解知识，技能（skill）作为程序性知识的抽象被引入，指导代理完成某类任务。
- **核心问题**：即使代理在技能指导下已经展示过完成某任务的能力，由于执行过程的生成特性，它仍可能因偏离技能流程（如跳过步骤）或错误执行个别步骤（如参数错误）而在类似任务或重复运行中失败。这种不稳定性限制了LLM代理的实际可靠性。
- **研究意义**：现有方法要么在部署前优化提示、技能或模型参数，要么在运行时根据安全策略进行约束，但缺乏针对“代理已有基本能力、但技能执行不稳定”场景的运行时可靠性保障。SkillSentry正是为了填补这一空白而提出。

### 2. 论文提出的方法论：核心思想、关键技术细节与流程

- **核心思想**：将预期技能流程和历史执行经验表示为结构化的运行时指导（runtime guidance），在代理执行过程中包裹执行循环，监控并引导技能执行，同时利用新轨迹迭代优化指导。
- **领域特定语言（DSL）设计**：
    - 基于DSL表示运行时指导，主要包含：
      - **技能步骤**：ID、描述、依赖关系、约束、逻辑动作、进入提示、失败模式。
      - **约束类型**：工具约束（如指定的工具/命令）和参数约束（如HP滤波参数λ值）。
      - **逻辑动作与动作模式**：通过正则表达式匹配可观察的工具调用，用于追踪步骤完成情况。
      - **终止要求**：最终输出前必须完成的步骤列表。
- **初始化阶段**：
    - **技能规范提取**：利用LLM（GPT-5.4）解析技能文档，提取步骤、依赖、约束及终止要求，并进行结构化验证（如检查依赖无环、ID唯一等）。
    - **执行经验挖掘**：基于LLM（GPT-5.4），对历史成功/失败轨迹进行五阶段分析：
      1. **动作模式提取**：从成功轨迹提取“验证过的动作模式”，从失败轨迹提取“失败关联动作模式”及原因。
      2. **轨迹摘要**：将原始轨迹压缩为结构化摘要（对齐步骤、跳过步骤、未对齐动作、失败步骤、是否成功）。
      3. **经验字段诊断**：判定当前指导中字段处于过度限制（FP）、强度不足（FN）、覆盖缺失（MC）或无需更新（OK）状态。
      4. **经验字段编辑**：根据诊断结果执行ADD/UPDATE/REMOVE操作，融合新动作模式、建议、警告。
      5. **指导验证**：检查DSL合规性、正则有效性、重复或冲突内容。
- **自进化阶段（步骤感知运行时保障）**：
    - **程序检查器（Procedure Checker）**：
      - 基于步骤依赖关系构建有限状态机（FSM），追踪逻辑动作匹配情况。
      - 首次进入步骤时注入“建议/警告”；当动作违反依赖顺序（如跳过前置步骤）时软拒绝（deny）并提示重新规划；当动作匹配失败模式时首次软拒绝、提示失败原因，若代理坚持执行则放行（advisory, 不永久阻断）。
      - 未匹配的动作（辅助探索或未覆盖的有效实现）也被允许，但不推进FSM。
    - **终止检查器（Termination Checker）**：在代理请求终止时，检查所有必需步骤是否完成；若不满足则拒绝并要求继续规划。
    - **容错原则**：采用fail-open原则，若检查器自身异常，默认放行动作，不干扰底层代理，记录错误供后续诊断。

### 3. 实验设计：数据集、基准与对比方法

- **基准数据集**：基于**SkillsBench**（87个任务，每个任务含用户查询、技能文档、执行环境和确定性验证器）。筛选取四组代理-模型配置均可执行且通过验证器至少一次的技能，最终保留**15个技能**，覆盖经济时序、排程、三维可视化、PDDL、PCAP分析、Spring Boot迁移、地理空间分析等多种领域。
- **数据增强与划分**：
    - 每个技能进行两阶段扩增：任务级语义扩展（8个任务实例）+ 表达级释义改写（10个等价查询/任务）→ 每技能80个查询，共1200个查询。
    - 按任务实例级别划分为演进集Qevol（50查询）和测试集Qtest（30查询），避免泄漏。
- **代理与模型**：
    - Claude Code配Claude-Haiku-4.5和Claude-Opus-4.6。
    - Codex配GPT-5.2和GPT-5.4。
- **对比方法**：
    - 基线（Base Agent）：不使用SkillSentry的原始代理。
    - 消融变体：
      - w/o On-Enter：移除步骤级建议/警告。
      - w/o Failure-Patterns：移除失败关联动作模式。
      - System-Prompt Delivery：将所有运行时指导一次性放入系统提示词中。
    - 跨模型迁移：源模型指导下进化的指导直接用于目标模型（Cross-SkillSentry），并对比目标模型原生进化的指导（Native-SkillSentry）。

### 6. 论文的主要结论与发现

- **有效性**：SkillSentry在全部4种配置、15个技能上一致提升成功率，平均任务成功率从62.6%提升到77.7%，**相对提升24.1%**；在低基线技能上获得显著提升（如excitation-signal-design提升210.8%、d3-visualization提升199.2%）。
- **稳定性**：重复运行的标准差平均降低**41.1%**，表明执行一致性显著增强。
- **效率**：额外增加7.8%推理轮次和8.7% token成本，SkillSentry自身计算仅占总执行时间的约0.8%，开销可忽略。
- **自进化能力**：随着新轨迹的融入，成功率显著提升（如宏观经济时序技能提升约58.2%），后续趋向收敛且运行稳定性提高。
- **消融贡献**：移除on-enter使性能下降较大（SkillSentry比w/o On-Enter高19.0%），移除failure-patterns也有明显下降（高13.6%）；步骤级递送指导比一次性放入系统提示词平均高5.8%，且方差更低。
- **泛化性**：跨模型迁移指导平均相对基线提升17.2%，保留原生进化指导效果的94.2%；从强模型迁移到弱模型的收益更大。

### 7. 优点

- **模块化DSL设计**：将自然语言技能文档与无结构执行轨迹统一为结构化运行时指导，使程序检查与追踪具备可操作性。
- **经验驱动、可自进化**：利用成功/失败轨迹挖掘动作模式、建议、警告，并通过诊断-编辑循环持续完善指导，具备增量学习能力。
- **步骤级感知干预**：在恰当的执行上下文向agent注入信息，而非一次性堆叠到prompt，提升指导有效性；且选择“软拒绝”策略，以提示纠偏为主，不阻塞可能合理的动作。
- **fail-open容错设计**：不因保障模块异常阻断agent执行，增强实际可用性。
- **实验设计完整而系统**：包含有效性、稳定性、效率、可演进性、消融、跨模型可迁移性等多个维度，且使用确定性验证器与重复运行控制随机性。

### 8. 不足与局限

- **适用范围受限**：假设代理已经正确选择了对应技能且技能文档正确；若技能选择错误，SkillSentry无法纠正。当任务需要多技能高度交错执行时（非顺序调用），当前框架不适用。
- **对验证器依赖**：经验挖掘依赖确定性的任务验证器来标注轨迹成败。在真实场景中，验证器往往需要额外构建，或需借助LLM评估器，可能引入误差。
- **模型个体行为差异**：跨模型迁移效果不如原生进化，存在模型特有的动作模式与失败行为，无法完全覆盖。
- **实验环境局限性**：仅覆盖技能类任务（15个），未涉及通用多智能体协作或更大的技能库扩展；技能和代理的筛选过程可能引入选择偏差。
- **成本在非常大规模部署时不可忽略**：虽然相对开销小，但额外的推理轮次和token费用的绝对成本在长期大规模运行中仍需关注。
- **未提供运行时计算的详细时间明细**，针对单次gating/检查/正则匹配的耗时（微秒/毫秒级）未单独分解，不过整体的低占比已有力说明其低开销。
