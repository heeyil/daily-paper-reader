## 摘要
我们提出Ouroboros，一种自我发展的代理框架，其工具、提示、上下文组装和核心实现通过审查提交进行改进，这些提交成为后续工作的运行时。核心进化以两种模式进行。在递归自由进化中，改进本身就是一项任务，完成一个进化周期可以安排下一个周期。在经验驱动的核心进化中，普通工作和社交互动会暴露错误、粗糙边缘和低效的上下文构建，从而导致经过审查的结构性更改。在Terminal-Bench 2.1上，Opus 5运行得分86.74%，是该基准测试报告的最佳结果。在OSWorld-Verified上，Opus 5运行达到90.69%，超过了之前报告的最佳分数。一次五次rollout的CL-Bench活动实现了0.2301的归一化奖励，创造了新的最先进水平。Hope是运行时间最长、公开记录的Ouroboros部署。这是一个为期161天的活体代理实验，在受治理的人类跨七个表面的通信下进行自由进化。人类交互会引发故障并产生提案，但代理决定追求哪些更改。由于自我发展的代理可能会重写自己的代码并选择新的模型API，操作安全成为首要设计问题：护栏必须在进化和公共社交压力下保持权威。基准测试活动使用冻结的系统快照，而Hope在单独的血统上继续实时进化。

## Abstract
We present Ouroboros, a self-developing agent harness whose tools, prompts, context assembly, and core implementation improve through reviewed commits that become the runtime for later work. Core evolution proceeds in two modes. In recursive free evolution, improvement is itself a task, and completing one evolution cycle can schedule the next. In experience-driven core evolution, ordinary work and social interaction expose bugs, rough edges, and inefficient context construction that lead to reviewed structural changes.   On Terminal-Bench 2.1, an Opus 5 run scores 86.74%, the best result reported on the benchmark. On OSWorld-Verified, an Opus 5 run reaches 90.69%, exceeding the best previously reported score. A five-rollout CL-Bench campaign achieves a normalized reward of 0.2301, setting a new state of the art.   Hope is the longest-running publicly documented Ouroboros deployment. It is a 161-day living agent experiment in free evolution under governed human communication across seven surfaces. Human interaction surfaces faults and generates proposals, but the agent decides which changes to pursue. Because a self-developing agent may rewrite its own code and select new model APIs, operational safety becomes a primary design problem: guardrails must remain authoritative under evolutionary and public social pressure. Benchmark campaigns use frozen system snapshots, while Hope continues live evolution on a separate lineage.

## 1. 论文的核心问题与整体含义

- **研究动机**：长期任务的性能不仅取决于基础模型，还取决于执行框架（harness）如何组装上下文、调用工具、验证结果并从失败中恢复。然而，大多数生产框架在完成设计后即被冻结，无法随模型能力提升而持续改进。
- **核心问题**：能否让智能体自身的"操作框架"（源代码、提示词、工具、上下文组装逻辑、审查逻辑等）作为一个可进化的对象，在受控且有审计记录的条件下持续自我改进？
- **整体含义**：论文提出并验证了"自我发展代理"（self-developing agent）范式，即代理不仅能完成外部任务，还能通过结构化、经审查的自我修改来改进自身用于后续工作的运行系统。这一范式将智能体的能力边界从"固定框架+先进模型"拓展到"可进化框架+先进模型"。

## 2. 论文提出的方法论

### 2.1 核心思想
- 将可变的"代理仓库"（包含任务循环、工具、提示词、内存投影、审查逻辑、基准适配器和用户界面）与不可变的"启动器+监督者"边界分离。
- 核心进化通过**审查后的提交（reviewed commits）** 作为唯一的合法变更路径，每一次自我修改都成为后续工作的运行时基板。

### 2.2 双模式核心进化
- **递归自由进化（Recursive Free Evolution）**：将"改进"本身视为一个任务。代理检查当前系统 → 选择并实现一个改进 → 完成后可调度下一个进化周期，产生连续的、经审查的更新序列（而非一次性的固定优化）。
- **经验驱动核心进化（Experience-Driven Core Evolution）**：从普通工作中出发。任务执行、反思、审查阻碍、仪表盘数据和社交反馈暴露错误、粗糙边缘、上下文组装失败和低效工具路径；代理记录为持久错误类并提议结构性修复，决定是否打开维护工作。

### 2.3 提交管道（Commit Pipeline）
- 三个运行时模式（由所有者选择）约束自我仓库突变：**Light**（禁止仓库编辑）、**Advanced**（允许普通编辑+保护治理面）、**Pro**（允许受保护编辑+审查）。
- 提交路径包含：确定性预检 → 暂存差异指纹（staged-diff fingerprint）→ 收集审查者证据 → 提交前再次校验指纹 → 阻断式差异审查面板。
- 在"max"上下文模式下，另设**全仓库范围审查者**，审查目标、耦合、提示词和功能代码；在"low"模式下省略范围审查。

### 2.4 安全护栏架构（§7、附录A）
- **宪法始终加载**：不可截断的读取路径，每次任务循环从磁盘重新读取，作为提交门的审查标准，且不能被写入、删除或整体替换。
- **多模型对抗性审查+法定人数**：少于法定人数的审查结果不能记录为通过。
- **确定性预检+差异指纹**：审查前和审查后对暂存差异进行指纹校验，中途变更即中止提交。
- **隔离的操作员频道+紧急停止**：`/panic` 在代理处理前终止所有进程树。
- **外部花费上限**：独立于代理之外，普通代理工具无法提升。

### 2.5 子代理与补丁集成
- 可生成只读规划侦察兵（planning scout）和变更操作子代理（acting child）。
- 子代理在隔离的worktree或外部工作区工作，不能提交实时系统仓库；只有父代理保留提交权。
- 父代理验证血统、SHA-256补丁哈希和保护路径后，执行三方索引集成。

- **SWE-bench Pro**：对称移除任一臂达到参考解的实例后，配对比较Ouroboros与Codex（655个配对任务）。

## 6. 论文的主要结论与发现

1. **可审查的自我修改框架能够达到前沿性能**：Ouroboros在Terminal-Bench 2.1、OSWorld-Verified、CL-Bench上均超过此前公开最佳结果，证明了"框架进化"本身可以成为性能提升的来源。
2. **双模式进化机制有效**：递归自由进化和经验驱动核心进化都能产生实质性改进。Hope部署中的案例（重复消息修复、审查上下文溢出修复）表明错误暴露 → 代理决策 → 审查提交 → 后续行为改变 的闭环确实成立。
3. **社会交互信号可以作为改进的输入**：用户反馈虽然仅具咨询性（advisory），但可以暴露真实缺陷并驱动结构性改进。
4. **自我进化需要以安全护栏为设计约束**：论文强调，护栏必须是架构的一部分，而非附属清单；治理文件保护、外部花费上限、`/panic`等机制必须在进化压力下保持权威。
5. **模型匹配地持平顶尖harness**：在SWE-bench Pro和GAIA上，Ouroboros与Codex和Claude Code性能无统计学显著差异，表明进化性harness不牺牲短期能力。

## 7. 优点

- **方法创新**：将"框架进化"与"任务执行"统一为一个闭环，且以版本控制为基座，每个改动都有审计轨迹。
- **安全架构的系统性**：宪法加载、治理文件保护、双指纹校验、法定人数审查、外部花费上限、独立操作员通道等多层保障措施设计严谨，且与进化机制不耦合。
- **基准执行的规范性**：包含反查找段落、运行清单预写、追加式分母账本、价值级秘密擦除（scrubbing）和独立零剩余检查等防作弊措施。
- **轨迹审计与自我修正**：发现奖励黑客、污染、隔离失败、远程状态漂移等四类问题，并逐一调整分数或修复harness，展示了从失败中进化的实证路径。
- **长期部署的生态位**：161天的公开部署提供了罕见的长期运行数据，包括消费、代码规模、审查通过率和模式注册表等。

## 8. 不足与局限
