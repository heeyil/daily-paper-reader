## 摘要
扩展智能体能力的研究主要集中在改进模型上，然而交互式智能体通过运行时框架来行动，该框架协调上下文、工具、控制流和停止条件。框架既决定了模型能完成的任务，也决定了其学习的轨迹。这种耦合促使模型-框架协同进化以实现递归自我改进：为固定模型构建框架，根据经过验证的兄弟轨迹更新模型，并随着模型能力的变化重建框架。实现这一循环需要一种受控的方式来演进框架，同时保持干预的标识与效果。我们提出了HELIX，一种用于框架演进的可溯源基座。HELIX将智能体系统分解为类型化端口、可复用原子组件、配方、产品外壳和运行时策略。它在保留轨迹、测试结果和来源的同时，使干预明确且可审计。因此，框架演进承担两个关联的角色：改进固定模型的执行，并产生匹配的成功案例、回归问题、接近成功案例和替代解决方案，作为后续模型改进的数据。我们在代码修复任务上对HELIX进行了一轮演进评估。一个包含65个候选方案的投资组合发现了一个固定框架，其任务覆盖率比Pi提高了4.0%，而完整投资组合通过互补的兄弟行为暴露了多达58.0%的额外经验证覆盖率。选定的候选方案通过重复运行和SWE-bench评估器进行评估。一个包含200个槽位的兄弟切片产生了438条经过验证的SFT、批评者、过滤器和偏好记录。这些结果表明了框架、模型和数据如何形成一个反馈系统：框架演进扩展了当前能力，并为下一个模型创造学习信号；模型更新则推动下一轮框架演进。HELIX为研究这一递归过程提供了可审计的接口。代码可在https://github.com/HKUDS/HELIX获取。

## Abstract
Scaling agent capability has largely focused on improving the model, yet an interactive agent acts through a runtime harness that mediates context, tools, control flow, and stopping. The harness shapes both what a model can accomplish and the trajectories from which it learns. This coupling motivates model-harness co-evolution for recursive self-improvement: build harnesses for a fixed model, update the model from verified sibling trajectories, and rebuild the harnesses as model capabilities change. Realizing this loop requires a controlled way to evolve harnesses while preserving intervention identity and effect. We present HELIX, a source-traceable substrate for harness evolution. HELIX decomposes agent systems into typed ports, reusable atoms, recipes, product shells, and runtime policies. It makes interventions explicit and auditable while retaining trajectories, test outcomes, and provenance. Harness evolution thus serves two linked roles: improving fixed-model execution and producing matched successes, regressions, near misses, and alternative solutions as data for subsequent model improvement. We evaluate HELIX in one evolution round on code repair. A 65-candidate portfolio discovers a fixed harness that improves task coverage by 4.0% over Pi, while the full portfolio exposes up to 58.0% more verified coverage through complementary sibling behavior. Selected candidates are assessed with repeated runs and the SWE-bench evaluator. A 200-slot sibling slice yields 438 verified SFT, critic, filter, and preference records. These results show how harness, model, and data form a feedback system: harness evolution expands current capability and creates learning signal for the next model; model updates motivate the next round of harness evolution. HELIX provides an auditable interface for studying this recursive process. Code is available at https://github.com/HKUDS/HELIX.

#### 2.1 核心思想：模型-框架协同进化

  - **任务内快速交互回路**：框架构造上下文并暴露动作，模型返回消息和工具调用，框架检查并执行动作，返回下一观察或停止。
  - **跨轮次慢速改进回路**：验证过的经验同时用于更新模型（θₜ → θₜ₊₁）和重建框架组合（Φₜ → Φₜ₊₁）。

#### 2.3 HELIX 系统：六个实体与三层设计

- **六个实体**：port（稳定能力槽）、atom（通用原子/personality 原子）、pack（原子组）、recipe（一个显式声明的候选框架）、product shell（SDK/CLI/TUI/Web 入口）、runtime policy（权限与执行约束）。

  3. **重建**：模型更新后，同一合约可复用但配方为新能力画像重新修订。

- 每次运行与 recipe 和 lockfile 连接，保留模型-任务-尝试身份、运行时轨迹、工作区差异、验证器结果、策略证据——**保留干预身份，不将结果压缩为单个成功比特**。

### 6. 论文的主要结论与发现

**Finding 1（执行提升）**：65 候选矩阵中最佳固定框架从 Pi 的 50/100 提升到 52/100（相对 +4.0%）；重复 LCB 评估中 OpenCode 家族成员达 75/100（Pi 为 72/100）；SWE-bench 上选定成员达 46/55（Pi 为 44/55）。但**偏好成员随评估协议变化，没有通用最优框架**。

**Finding 2（组合广度与选择必要性）**：
- 完整 65 候选组合的 post-hoc 并集覆盖 79/100 任务（+58.0% 相对提升），在 SWE-bench 上并集 49/55 超过最佳单体 46/55。
- 但 64 个非基线候选中仅 2 个超过 Pi，23 个为 0 分——**盲目组合不可靠，必须配合类型化门控、廉价筛查和自适应选择**。

**Finding 3（数据产出）**：200 槽位 SWE-bench 切片导出 438 条多样化的训练记录（154 偏好对、113 过滤样本、63 清洁 SFT、56 需清洗 SFT、52 critic 负样本），且按实例划分 train/dev（16/4），无泄漏。

**核心机制发现**：
- 配对案例显示**目标测试通过≠可用的训练正样本**（Pytest 案例：通过 2/2 F2P 但破坏 2 个 P2P 回归）。
- **补丁干净≠语义正确**（Xarray 案例：同样干净的补丁因 fallback 语义不同而分化为 gap/resolved）。
- 框架进化存在**可复现的修复闭合机制**（LCB v6-025 案例）和**反例**（v6-088 中双重组均退化），排除了“更活跃的框架更好”的简单叙事。

### 7. 优点：方法或实验设计上的亮点

1. **问题定义精准**：明确拒绝“模型与框架独立进化”的错误不对称性，将 RSI 的改进单位从模型提升到系统级状态 Zₜ = (M, Φ)。
2. **可审计的干预表示**：用端口-原子-配方-产品壳-策略的五层实体将 ad-hoc 提示改写为显式、可枚举、可编译的干预；lockfile 保证确定性复现。
3. **双重输出设计**：框架进化同时产出“当前执行提升”和“下轮模型更新数据”，最大化每次回滚的计算价值。
4. **细粒度验证标签**：不将结果压缩为成功/失败二值，而是保留 resolved/regression/near-miss/no-action/policy-violation 等多级标签，支撑 critic、filter、preference 等多样性训练目标。
5. **证据链接的兄弟轨迹**：同一模型+任务跨框架的配对比较从日志恢复变为构造性产物，且保持训练/开发集按实例分割，防止配对泄漏。
6. **机制级案例分析**：Pytest 和 Xarray 的逐步骤轨迹表展示了“为什么干净补丁仍是负样本”的具体机制，非仅堆砌数字。
7. **诚实评估分离**：明确区分固定框架覆盖率、post-hoc 并集覆盖率与可部署路由，避免将 oracle 结果伪装为在线性能。

### 8. 不足与局限

1. **实验覆盖狭窄**：仅覆盖编码智能体（LCB + SWE-bench），不涉及网页导航、通用工具使用或多智能体场景；LCB 只测公开测试，不反映隐藏测试表现。
2. **因果归因缺失**：每个配方同时改变多个组件（session/hooks、config、tools 等），无法判定哪个组件驱动改进；作者承认需要逐组件消融。
3. **选择偏差与协议不一致**：主矩阵（1 次/任务）、重复运行（10 次/任务）、SWE-bench（2 次/任务）预算不同，排名不可直接比较；选定成员进行深度验证引入了选择效应。
4. **自动化评估的固有局限**：补丁可能通过修改测试或利用评估器漏洞而“成功”；超时或环境损坏可能掩盖正确补丁；部分案例仍需人工审查。
5. **未闭环验证**：论文仅物化训练数据，未实际执行模型更新；缺少多轮 build-update-rebuild 的端到端实验，递归性在实证上未得到完整验证。
6. **安全与维护问题**：组件来源混合可能产生不安全权限组合；上游框架更新后需重新验证集成与安全策略；由未选中候选生成的轨迹可能编码接口损坏伪影而非稳健问题求解能力。
7. **算力透明度不足**：未报告 GPU 型号/数量/token 消耗，影响实验可复现性和成本评估。
