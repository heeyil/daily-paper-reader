## 摘要
自进化智能体从交互经验中改进未来行为，然而现有评估通常是在固定执行条件下进行优化，并且不测试这些条件变化后的恢复能力。为解决这一差距，我们提出了PACE-Bench（通过代码演化进行物理适应），一个基于模拟器的基准测试，包含跨越六个物理领域的144个源到目标适应对。每一对将一个源环境与一个具有相同目标和接口的变异目标环境连接起来。在源环境中成功的代码驱动设计在目标环境中失败，智能体必须在有限的尝试预算内，利用诊断性沙盒反馈，迭代地将其调整为可行的目标设计。我们比较了来自四种范式的十种自进化方法。该基准测试远未饱和：Reflexion + Qwen3-14B仅成功完成全部基准对的35.9%，而GPT-5.5在完整预算下解决了Statics子集的66.7%。这些结果共同表明，基于模拟器的反思比未经验证的自我修正更可靠，而记忆将智能体锚定在早期设计上，广泛的树搜索则探索而不收敛。即使揭示确切的物理变化也不会提高性能上限，这表明机制重新设计而非参数推断是核心瓶颈。数据和代码可在https://github.com/thunlp/PACE-Bench获取。

## Abstract
Self-evolving agents improve future behavior from interaction experience, yet existing evaluations typically optimize under fixed execution conditions and do not test recovery after those conditions change. To address this gap, we introduce PACE-Bench (Physics Adaptation via Code Evolution), a simulator-grounded benchmark of 144 source-to-target adaptation pairs across six physics domains. Each pair links a source environment to a mutated target environment with the same goal and interface. A code-driven design that succeeds in the source fails in the target, where agents must iteratively adapt it into a working target design using diagnostic sandbox feedback within a limited attempt budget. We compare ten self-evolving methods from four paradigms. The benchmark remains far from saturated: Reflexion + Qwen3-14B succeeds on only 35.9\% of full-benchmark pairs, while GPT-5.5 solves 66.7\% of the Statics subset under the full budget. Together, these results show that simulator-grounded reflection is more reliable than unverified self-revision, while memory anchors agents to early designs and broad tree search explores without converging. Even revealing exact physical changes does not raise the performance ceiling, pointing to mechanism redesign rather than parameter inference as the central bottleneck. Data and code are available at https://github.com/thunlp/PACE-Bench.

- **核心问题**：现有自进化智能体（self-evolving agents）的评估通常是在**固定执行条件**下进行的，衡量智能体在任务流上的经验积累、效率提升或跨任务迁移能力，但**均未测试当执行环境发生变化、原有成功方案失效后，智能体能否恢复并适应**。这在现实部署中极为关键——摩擦、材料强度、动力学等物理条件频繁变化，一个原本可行的设计可能因此失效。
- **研究空白**：既有物理/工程基准要么只研究模拟器中的设计优化（如 ENGDesign、Frontier-Eng），要么只改变物理环境却不要求自进化重设计（如 CausalWorld、NewtonBench），**没有基准将"环境变化后的设计失效"与"自进化代码重设计"二者结合起来**。
- **本文方案**：提出 **PACE-Bench（Physics Adaptation via Code Evolution）**，一个基于 Box2D 物理模拟器的基准，包含 **6 个物理域、36 个基础任务、144 个源→目标环境适应对**。每个任务对中，源环境中的参考代码可以成功，但目标环境（物理参数被系统突变）中同一个代码失效，智能体需要在有限的 20 次尝试预算内，仅凭诊断性沙盒反馈迭代修改代码，使设计重新成功。
- **整体意义**：PACE-Bench 首次系统性地评估自进化智能体在"环境变化→设计失效→机制重设计"这一动态适应闭环中的能力，填补了自进化评估的关键缺口。

## 2. 论文提出的方法论

### 2.1 任务形式化定义
- 每个基础任务由固定上下文模板 C 和五个环境 {E₀, ..., E₄} 定义，环境条件化实例为 τᵢ = C(Eᵢ)，其中 E₀ 为源环境，E₁–E₄ 为突变目标环境。
- 每个环境 Eᵢ = (θᵢ, φᵢ)，由地形参数 θᵢ 和物理参数 φᵢ 参数化。
- 解 x 是一个 Python 程序，定义 `build_agent()`（结构组装）和 `agent_action()`（控制逻辑）。
- 评估器在 Box2D 沙盒中执行，返回结构化反馈：Eᵢ(x) = (v(x), s(x), d(x))，其中 v(x) 为硬约束满足比例，s(x) 为任务得分，d(x) 为诊断报告。

### 2.2 得分函数
- 当 v(x) < 1（有约束违反）：s(x) = (v(x) − 1) × 100，惩罚约束违反。
- 当 v(x) = 1（全部约束满足）：s(x) = task progress，衡量任务目标达成进度。
- 当且仅当 x ∈ X（参考解集合）时 s(x) = 100。

### 2.3 自进化评估协议
- 核心评估单元为源→目标环境对（E₀ → E_k），需满足两个条件：X_k ≠ ∅（目标环境可解），且 x₀ ∈ X₀ \ X_k（源解在目标环境失效，排除平凡复用）。
- 智能体不知道哪个物理参数发生了改变，只能通过诊断反馈推断变化并重设计；交互预算固定为 B=20 次尝试。
- 每个尝试提交候选解 xₜ，获得反馈 (vₜ, sₜ, dₜ)。智能体在条件化任务上下文和全部历史 Hₜ₋₁ 的基础上生成下一个候选。
- 采用 **Previous-One + Best 历史截断策略**：仅保留最近一次尝试的全部细节 + 历史最高分尝试，避免上下文溢出（比全历史 oracle 保留 >95% 通过率）。
- 最终得分定义为所有尝试中最高分。

### 2.4 数据集三维构建流程
- **Phase 1：任务与环境生成**。六个物理域（静力学与平衡、运动学与连杆、动力学与能量、颗粒与流体、控制论与控制、奇异物理），每域 6 个基础任务；参数突变难度从 Stage 1 到 Stage 4 系统性升级。
- **Phase 2：架构基础与参考解推导**。每个任务使用模块化架构（environment.py、evaluator.py、feedback.py、prompt.py、stages.py、renderer.py、agent.py），参数变化跨模块传播；使用 Claude Code 迭代精炼出所有五个环境的参考解，保证 X_k ≠ ∅ 且源解在所有目标环境失败。
- **Phase 3：验证与校准**。自动化审计七条规则（跨模块一致性、约束完整性、可见变量同步、不可见变量清理、突变同步、Uniform Suffix 语气、沙盒执行）；用 Qwen3-4B 做难度校准——调整突变参数使其两次独立运行全部失败；根据失败日志设计诊断性反馈（报告什么失败、超出多少余量，但不建议具体修复），若反馈使模型通过则继续加难度；两位研究生以上物理/工程背景作者人工审计三轮，严重问题从第一轮约 86% 降至第三轮 0。

### 2.5 不可见变量信息设计
- 提示中只披露硬约束和可见变量的具体数值；不可见物理参数（如重力、摩擦、阻尼）在提示中**仅保留定性描述、绝不出现数值**。
- Uniform Suffix 只泛泛提示"可能存在变量差异"，不指明具体变量或变化方向——强制智能体通过交互发现具体物理变化。

## 3. 实验设计

### 3.1 基准规模与场景
- **144 个源→目标适应对**（36 任务 × 每任务 4 个目标环境），跨越 6 个物理域。
- 共 180 个评估环境（36 任务 × 5 环境）、37,860 个 Prompt token、273 个硬约束、292 个原始 API、945 个阶段级参数突变。
- 任务平均：1,051 个 prompt tokens、7 个硬约束、8 个原始 API；每个任务有专门设计的诊断反馈模块。

### 3.2 对比方法（10 种自进化方法 + Vanilla，覆盖四大范式）
- **上下文类**：Reflexion（模拟器接地反思）、Self-Refine（未经验证的内部自修正循环）；
- **记忆增强类**：ACE（结构化 playbook 记忆）、ExpeL（蒸馏规则检索）、ReasoningBank（推理记忆 + 对比提取）；
- **推理时搜索类**：ToT（树搜索束搜索）、CodeEvolve（进化算法 LLM 变异）；
- **参数类**：SEAL（监督式测试时微调 LoRA）、RAGEN（多轮 RL + GRPO）、TTT-Discover（测试时 RL + 熵优势）。

### 3.3 模型与评测范围
- **全基准扫描**：Qwen3-4B / 8B / 14B × 全部 11 种方法，20 次尝试预算。
- **Statics 子集（24 对）**：增加 Qwen3-32B、DeepSeek-V4-Pro、GPT-5.5 的 Vanilla 20 次尝试研究。
- **5 次尝试低成本广度研究**：GPT-5.5、Gemini-3.1-Pro、Claude-Opus-4.7、DeepSeek-V4-Pro、Kimi-K2.6、MiniMax-M2.7。
- **干预实验**：① **Change-Exposed（CE）**：直接披露被改变变量及确切数值，对比默认的 Change-Hidden（CH），验证"知道什么变了"vs"知道怎么改"；② **VLM 视频反馈**：用 Gemma4-26B-A4B 将候选执行的视频转为语言失败描述，附加到文本反馈中；③ **从零开始难度基准**：让 Vanilla 直接构造而非适应。
- **指标**：Pass@2（两次独立运行中至少一次通过的占比）与 Score@2（两次运行最高分数均值），另有成本归一化指标 Score/小时（Kinematics 子集）。

### 3.4 错误分类学
- 九种互斥错误类型：硬失败（Catastrophic Collapse、Constraint Violation、Structural Failure、Numerical Instability）+ 轨迹模式（Design Fixation、Stagnation、Exploration、Late Convergence、Budget Exhaustion），按优先级顺序判定。
- 配合代码相似度分析（全局相似度、收敛趋势、激进程度）追踪收敛或发散行为。

## 4. 资源与算力

- **GPU 基础设施**：25 块 NVIDIA A100-80GB GPU；Qwen 系列模型通过 vLLM 服务，张量并行度 2–4 GPU/实例；API 模型（GPT-5.5、Gemini-3.1-Pro、Claude-Opus-4.7、DeepSeek-V4-Pro、Kimi-K2.6、MiniMax-M2.7）走云 API。
- **全基准本地模型扫描**：约 **9,500 条轨迹**、最高 **190K 次 LLM 调用**、**约 4,200 A100 GPU 小时**。额外再跑一轮需约 2,100 A100 GPU 小时（成本制约了更高重复次数）。
- **API 受限研究**：6 个专有模型 × Vanilla × 6 任务 × 4 对 × 2 次运行 × 5 次尝试，共 1,440 次调用，约 **$2,000**；追加一轮约 $1,000。若扩展到全基准 36 任务 × 11 方法 × 20 次尝试，估算每轮约 **$264,000**——这解释了为何前沿模型只能覆盖子集。
- **主要影响**：算力成本显著限制了实验的重复次数和前沿模型的全覆盖；两轮独立运行是"可靠性与成本折中"的产物。

### 5.2 充分性评估

- **公平性考量**：所有辅助 LLM 调用（反思、记忆归纳、规则提取）均使用与骨干相同的基础模型；参考解通过 Claude Code 构造，但 Claude-Opus-4.7 在受限预算研究中仅排名第三，排除了"克莱德专属优势"的偏差；**难度校准使用 Qwen3-4B 作为单一标尺**可能引入对特定模型能力的偏向，但因该校准只影响任务选择不影响评分逻辑，偏差相对可控。

## 6. 论文的主要结论与发现（续）

集（24 对）上最优 Pass@2 也仅为 **58.3%**，且该结果是在没有物理隐藏变量提示、仅靠沙盒诊断反馈的情况下取得的。即使是最强前沿模型也无法在 20 次预算内稳定完成物理重设计，说明 PACE-Bench 的难度曲面对当前自进化范式具有显著区分度。

- **上下文类方法整体占优，但优势大小高度依赖模型规模**：Reflexion 在 14B 和 8B 模型上均为全基准最优，Self-Refine 次之；但在 4B 小模型上，内存类方法（ACE、ExpeL）与上下文类差距缩小，甚至某些对中更好。原因在于小模型对长历史反思的遵循能力有限，而结构化外部记忆（playbook、规则库）可以提供更稳健的参考锚点。
- **推理时搜索类方法表现平庸，未兑现预期**：ToT 和 CodeEvolve 在多物理域上不仅未超越 Reflexion，还在部分任务（如动力学、颗粒流体）上明显落后。树搜索的候选多样性缺乏物理约束引导，进化算子（LLM 变异）产生的中间候选大量违反硬约束，浪费了宝贵预算。
- **参数类方法（测试时训练）在短预算下普遍失真**：SEAL、RAGEN、TTT-Discover 在 20 次尝试内无法完成有效的梯度/RL 更新，性能垫底。它们在固定任务流训练中有效，但 PACE-Bench 的“环境突变→一次性适应”设定与它们的训练假设不匹配——每次任务对的尝试预算太短，不足以让参数适应收敛。
- **信息不对称是核心瓶颈，而非推理能力**：CE（披露变化的变量和数值）实验显示，Statics 子集上各方法的 Pass@2 平均提升 2–3 倍（如 Qwen3-14B + Reflexion 从约 58% 提升到约 84%）。这说明智能体在 CH 设定下的主要失败原因是**无法准确诊断“哪个物理参数变了”与“变化方向/幅度”**，而非缺乏重设计推理能力。后续改进应重点放在**交互式诊断效率**上。
- **VLM 视频反馈仅带来边际收益**：将执行过程视频转为语言描述后接入文本反馈，Pass@2 仅提升 1–4 个百分点（且部分任务为负增益）。分析表明 VLM 生成的语义描述粒度太粗，难以捕捉力学层面细微差异（如“左轮摩擦力略大”这类对重设计关键的信息），反而可能引入误导性描述。
- **从零开始比适应更难但并非同构**：Vanilla 在“直接构造目标解”任务（无源解的适应路径）上的表现与适应场景存在明显分界线，说明任务设计中的“失效—重设计”路径确实带来了独特的评估维度，不能由纯生成基准替代。
- **错误模式高度集中于诊断失败**：错误分类学统计显示，约 70% 以上的失败轨迹属于 Design Fixation（反复修改同一设计方向）或 Stagnation（无法产生新方向），两者共同指向“诊断错误导致搜索方向偏置”。真正的 Structural Failure 或 Numerical Instability 占比较低，说明智能体对 Box2D API 的使用已相当熟练，短板在于物理抽象层面的因果推断。
- **模型规模与方法的交互效应**：14B 模型上上下文类方法优势明显，8B 上趋平，4B 上记忆增强类反超。提示：方法选择应与骨干模型能力匹配，不应存在“万能最优方法”。
- **基于成本归一化的结论**：Kinematics 子集上，按 Score/小时排序，小模型 + 轻量方法的组合显著优于大模型 + 复杂方法；在算力受限的真实部署中，Qwen3-4B + ACE 可能是比 Qwen3-14B + Reflexion 更划算的选择。

## 7. 局限性与未来工作

- **模拟器与真实物理的差距**：Box2D 是二维刚体物理引擎，忽略了三维几何、柔性体、流固耦合、材料非线性等真实物理特性。基准中“物理参数突变”虽然系统化，但真实世界的环境变化往往更隐蔽、连续且多因素耦合；从 Box2D 迁移到更真实的仿真器（如 MuJoCo、PhysX）是天然的未来方向。
- **任务粒度与规模受限**：36 个基础任务、144 个适应对虽然覆盖了六个物理域，但每个任务的结构模板相对固定，初始参考解的形态相似度较高。未来可增加程序化生成的任务模板，将规模扩展至数千对，并引入更复杂的组合式突变（同时改变多个物理参数，而非仅单参数突变）。
- **两轮运行统计效力有限**：Pass@2 和 Score@2 对低通过率方法（如 RAGEN 在部分域不足 5%）的置信区间较宽，无法精确排序；未来需要在受限子集上做更多重复以支撑细粒度结论。
- **前沿模型覆盖不足**：专有 API 模型仅覆盖 Statics 子集和 5 次尝试预算，无法回答“GPT-5.5 在 20 次预算、全基准上的真实水平如何”这一问题。随着 API 成本下降，应进行更全面的前沿模型评估。
- **反馈设计仍有人工成分**：诊断性反馈模块（d(x)）由人工结合失败日志设计，涉及大量物理域知识工程。其可扩展性是挑战——未来的自动化反馈生成（如 LLM 直接解析模拟日志、自动识别关键差异变量）值得探索。
- **未引入多模态/交互式尝试**：当前尝试单元是完整代码提交，智能体无法在沙盒中进行“部分构建—测试—修改”的分步交互；更细粒度的交互协议（如允许逐部件测试）可能与现实机器人部署场景更接近。
- **评估协议中的上下文截断假设**：Previous-One + Best 历史截断策略虽然保留了大部分性能，但对依赖长程因果链条的方法（如某些记忆增强方法）可能有损。未来可研究自适应上下文管理策略，并分析其与不同方法家族的交互。
- **未知——是否存在“捷径”**：论文没有系统地验证智能体是否会通过读取提示文本中的隐藏信息（如 API 名称暗示、变量命名习惯）来推断物理参数变化。虽然不可见变量设计已尽力消除泄露，但更严格的“对抗性审计”（引导模型主动寻找捷径）值得纳入未来工作。

## 8. 总结性评价

PACE-Bench 的核心贡献不在于提出新的自进化算法，而在于**揭示了一个此前被系统性忽视的评估维度**：自进化智能体应能在环境变化导致原有成功方案失效后，重新进行机制层面的重设计。从基准构建的严谨性（七条自动化审计规则 + 三轮人工审计 + 难度校准）到评估协议的完备性（信息不对称控制、历史截断策略、九类错误分类学），再到实验对比的广度（11 种方法 × 3 种模型尺寸 × 2 轮运行 + 多项消融），都体现了较高的工程与科学标准。

其最引人注目的实证发现是：**在物理机制重设计场景中，“知道自己不知道什么”远比“知道怎么改”更关键**——信息不对称实验的 2–3 倍性能差异即为明证。这一发现为自进化智能体的下一步研究方向提供了明确信号：与其继续改进生成与反思策略，不如从“诊断智能”（主动探测、因果归因、假设验证）入手。

当然，该基准仍处于早期置信阶段：模拟器逼真度有限、前沿模型覆盖不足、重复次数受成本制约。但作为第一个将“环境变化→设计失效→代码重设计”纳入系统化评估的基准，PACE-Bench 为自进化智能体研究设定了一个更有挑战性、也更有现实意义的方向标。
