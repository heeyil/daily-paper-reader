## 摘要
持久化AI代理在长时间跨度内累积版本化状态，但仅靠存储保留并不能识别权威状态。缺少显式控制平面时，模型、工具和后台工作线程未经协调的更新可能导致陈旧覆盖、未经审计的暴露以及自我授权的权限提升。我们认为，代理状态治理是一个基础设施层面的激活问题，将连续性定义为已接受分支头的无断裂、授权谱系。我们提出了连续性内核（CK），一种激活契约，将提交之外的候选评估与原子状态激活解耦。不可信组件针对精确的前驱头或精确的空缺提出类型化变更。一个简短的激活事务重新验证所有权、前状态权威性、新鲜度和效果唯一性，并记录一个稳定的处置结果（提交、拒绝、隔离或延迟）。只有提交才会原子地推进分支头并安装完整的接受单元（状态、权威、谱系、效果、结果和收据）。一个有界的可执行模型在2,808,230个可达状态和5,526,474个状态变更转换中验证了该协议，且零不变量违反。

## Abstract
Persistent AI agents accumulate versioned state across long horizons, but storage retention alone does not identify authoritative state. Without an explicit control plane, unmediated updates by models, tools, and background workers risk stale overwrites, un-audited exposures, and self-authorizing privilege escalation. We argue that agent state governance is an infrastructural activation problem, defining continuity as an unbroken, authorized lineage of accepted branch heads. We present the Continuity Kernel (CK), an activation contract that decouples off-commit candidate evaluation from atomic state activation. Untrusted components propose typed changes against an exact predecessor head or typed absence. A short activation transaction revalidates ownership, pre-state authority, freshness, and effect uniqueness, recording one stable disposition (Commit, Reject, Quarantine, or Defer). Only Commit atomically advances the branch head and installs the complete accepted unit (state, authority, lineage, effects, outcome, and receipt). A bounded executable model verifies the protocol across 2,808,230 reachable states and 5,526,474 state-changing transitions with zero invariant violations.

# 论文总结：Beyond Memory: A Transactional Continuity Kernel for Long-Lived AI Agents

## 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：长期运行的 AI 代理会持续积累记忆、用户画像、计划、工具状态和策略等版本化状态，但仅仅“存储保留”无法决定哪个版本是权威状态。模型、工具、后台压缩器、恢复工作线程等并发提交或冲突更新时，若缺少显式的突变控制边界，可能出现：
  - 陈旧重试覆盖最新状态；
  - 未提交状态被无审计地暴露；
  - 提案通过在自身提议状态中注入所需权限实现“自我授权”的特权提升。
- **整体含义**：论文将“连续性”（continuity）定义为**一个分支上已接受分支头的无断裂、经授权的谱系**，强调这是基础设施层面的状态激活保证，而非关于代理意识或行为同一性的哲学主张。作者的核心论点：**代理状态治理本质上是一个基础设施级的“激活契约”问题**。
- 核心区别：**连续性 ≠ 保留**。被拒绝或隔离的对象仍可存储，但不能从权威分支头到达；密码学承诺可强制这种可达性边界，但不能使推断记忆变得事实正确或使策略获得规范性合法。

## 2. 方法论：核心思想、关键技术细节与流程

### 2.1 核心思想

- 提出 **Continuity Kernel (CK)**，一种“激活契约”：
  - 将**未提交的候选评估**（off-commit candidate evaluation）与**原子状态激活**（atomic activation）分离；
  - 模型、工具、操作者被视为**不可信提议者**，可进行概率推理、网络获取和候选状态构造，但只有确定性 CK 控制平面可以推进权威分支头；
  - 每次提案必须针对**精确的前驱头**（exact predecessor head）或**类型化目标缺失**（typed absence）；
  - 慢速评估和证据获取发生在激活之前；短事务在激活时重新验证所有可变事实，并记录**一个稳定处置**。

### 2.2 系统模型

- 状态按分支组织：`k = (sid, bid)`；分支索引状态 `X[k]` 包含记忆、用户画像、工具配置、策略对象等。
- 分支头 `h` 和分支行 `B[k]` 的结构：
  - `h = ⟨sid, bid, seq, root, v, parentRef, lineageRef⟩`
  - `B[k] = ⟨h, status, writer, epoch, dirSeq, handoff, createdFrom⟩`
  - 头相等必须所有字段规范编码后完全一致。
- 抽象内核配置：`C = ⟨X, B, Γ, S, t⟩`，其中 `Γ` 为前状态权威上下文，`S` 为持久元数据存储，`t` 为可信事务时间。
- 签名提案：`τ = ⟨pid, target, expected, ops, a, req⟩`，其中 `ops` 是有序状态操作，`a` 是权威变更序列，`req` 声明所需证据。

### 2.3 激活协议（17 阶段谓词）

- 准备阶段在提交外进行：认证提议者、获取证据、运行被固定版本的转换函数、密封候选。
- 激活阶段在事务内按规范顺序求值谓词向量 `Gkind(C, P)`，只有全部通过（all-Pass）才接受；
- 典型的检查包括：
  - `TargetLookup`（分支存在/缺失）
  - `Allocation`（所有权分配有效）
  - `ExpectedHead`（精确前驱头匹配或类型化缺失）
  - `FreshnessInitial` / `FreshnessFinal`（两次新鲜度验证）
  - `Authorization`（基于前状态 `Γ` 或创建上下文 `ξk` 授权，而非提议上下文——防止自我授权）
  - `Decision`（策略结果独立于授权记录）
  - `CandidateBinding`、`EffectBinding`、`VersionBinding`、`WitnessBinding`、`WellFormedness` 等。
- 四种稳定处置：
  - `Commit`：原子安装完整接受单元，推进分支头；
  - `Reject`：永久验证/策略失败，不保留后继；
  - `Quarantine`：在权威头之外保留密封材料；
  - `Defer`：信任获取服务报告所需证据不可用。
- 每个处置对提案 ID 是**终态**；重试需新 ID，丢失响应通过查原 ID 解决。
- 完整接受单元：`Uaccept = {X′, Γ′, h′, B′[k], rC, O[pid]}`，所有内容一次原子事务安装。

### 2.4 生命周期操作

- **分支创建**：无前驱，使用类型化缺失 + 创建上下文 `ξk`；授权和新鲜度均基于序列化的 `ξk`。
- **写入者交接（Writer Handoff）**：基于单调版本化目录记录的小状态机，包括 Prepare → Fence → Activate（或 Abort/Retarget），确保源写入者先被移除，目标才能激活，避免双重写入者。
- **迁移（Migration）**：显式迁移转换，固定确定性的 migrator，必须符合当前策略和损失策略。
- **前向恢复（Restoration）**：创建新后继，`X′ = Restore_M(Xc, M_μ(Xk))`，路径掩码 `M` 决定哪些路径取检查点值，其余取当前值；权威、撤销、写入者 epoch、生命周期字段受保护。

### 2.5 收据与验证等级

- 收据绑定提案、处置、达到的阶段、决定性原因及当时证据；
- 四种证据等级：结构性（Structural）、内核证明（Attested）、重放（Replay）、包含性（Inclusion）；
- 强调签名不等于已提交，必须区分密码学签名与持久事务包含。

### 2.6 安全属性

- 三个主要命题：
  1. 所有者绑定且稳定的结果：一个提案 ID 最多一个持久处置；
  2. 单一精确后继：一个完整前驱或序列化缺失最多一个提交后继；
  3. 效果最多执行一次：每个效果 ID 最多一个接受绑定，包括在线记录回收后。
- 所有命题均基于 9 个显式假设（A1–A9），如原子序列化、完整上下文、非回收作用域等。

## 6. 主要结论与发现

- **状态保留不等于权威**：长期代理需要显式的“激活”控制平面，才能确定哪个状态版本成为权威分支头。
- **CK 激活契约有效**：通过分离候选准备与原子激活，能在不可信提议者环境下保证精确后继、预状态授权、效果最多一次、生命周期隔离等安全属性。
- **形式验证结果**：在 2,808,230 个可达状态和 5,526,474 个状态变更转换中零不变量违规，所有覆盖 witness 均达到。
- **防御对抗行为**：模型在 8.88M 次转换尝试中识别并拒绝了大量并发/重放攻击，例如 `RejectStaleHead`、`IdReuseConflict`、`ReclaimedEffects` 合计占 37% 的尝试。
- **核心贡献**：不是新的底层事务引擎，而是定义在标准事务基板上的“激活契约”，以及区分“存储保留”与“权威可达性”、“密码签名”与“事务包含”的原则性系统基础。

## 7. 优点

- **问题定位清晰**：将长期代理状态治理提炼为“激活契约”而非单纯存储或检索问题，具有系统视角的新颖性。
- **协议形式化程度高**：给出明确的系统模型、17 阶段激活谓词、四处置状态机、生命周期操作语义和收据验证等级，可实施性强。
- **安全属性有证明**：在显式假设下给出三个命题及证明思路，对条件边界坦诚。
- **有可执行验证模型**：通过有限状态空间穷举验证，覆盖多种并发、对抗、生命周期场景，提高协议可信度。
- **自我批判充分**：明确讨论抽象模型与物理存储实现之间的差距、签名与持久包含的区别、外部副作用原子性的限制、性能开销等。

## 8. 不足与局限

- **缺乏真实系统实现与测试**：论文仅验证抽象模型，未在 PostgreSQL、FoundationDB、Raft 等真实存储引擎上实现并测试，物理崩溃、WAL、网络分区等现实故障不在模型覆盖内。
- **有限验证范围**：BFS 深度仅到 7，状态空间受限，不能提供无限状态的数学正确性证明；模型由作者自己实现，可能存在实现偏差。
- **无对比实验**：没有与其他代理内存/事务系统（如 MemTX、MemTxn）进行实证比较，无法量化 CK 的额外开销和收益。
- **性能开销**：激活事务包含 17 阶段顺序检查、两次新鲜度验证、前瞻单元构造等，在 Python 中单次约 32μs；高吞吐场景下需要存储级优化，但论文未给出真实性能基准。
- **外部副作用无法原子化**：CK 的原子性仅限于自身状态边界，无法使不可逆的远程操作（如外部 API、物理执行）与内部状态更新原子化；只建议通过幂等 outbox 缓解。
- **对底层假设依赖强**：安全属性依赖 9 个假设（如原子序列化、密钥保护、完整上下文等），若底层存储不满足这些条件，保证将失效。
