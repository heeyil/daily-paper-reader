## 摘要
基于LLM的代码智能体通过与代码库和工具的迭代交互，已经推动了仓库级软件开发的进步。然而，特性开发需要通过连贯的跨组件功能链将新行为集成到现有架构中。现有智能体通常通过自由形式推理推导此类功能链，常常产生不可靠的特性设计，功能链不完整。此外，文本设计难以验证和执行，使得在长期开发过程中维护设计与实现的一致性具有挑战性。我们提出CodeSpec，一种用于仓库级特性开发的双可执行规范方法。它通过将子需求语义与仓库架构进行证据配对来构建可靠的功能链，然后将它们编译为互补的架构和行为规范，这些规范检查链的完整性和正确性，同时在长期交互中保持设计与实现的一致性。在针对现有仓库特性开发的FeatureBench上，CodeSpec在使用DeepSeek-V4-Pro时达到70.7%、55.0%和49.9%的通过率，优于Claude Code等代表性基线。在仓库生成基准NL2Repo-Bench上的结果进一步证明了其泛化能力。

## Abstract
LLM-based code agents have advanced repository-level software development through iterative interaction with codebases and tools. However, feature development requires integrating new behaviors into existing architectures through coherent cross-component functional chains. Existing agents typically derive such chains through free-form reasoning, often producing unreliable feature designs with incomplete functional chains. Moreover, textual designs are difficult to verify and enforce, making it challenging to maintain design-implementation consistency throughout long-horizon development. We propose CodeSpec, a dual executable specification method for repository-level feature development. It builds reliable functional chains from evidence pairing sub-requirement semantics with repository architectures, then compiles them into complementary architecture and behavior specifications that check chain completeness and correctness while preserving design-implementation consistency over long interactions. On FeatureBench, which targets feature development in existing repositories, CodeSpec achieves 70.7%, 55.0%, and 49.9% pass rates under DeepSeek-V4-Pro, outperforming representative baselines such as Claude Code. Results on the repository generation benchmark NL2Repo-Bench further demonstrate its generalizability.

- **核心挑战**：
  - **设计不可靠**：现有智能体通过自由形式推理设计功能链，容易遗漏关键依赖或调用关系，导致功能链不完整或不一致。

- **整体目标**：提出一种**双可执行规范方法（CodeSpec）**，通过构建证据导向的功能链并编译为可执行的架构与行为规范，同时解决设计可靠性和长期一致性维护问题。

## 2. 论文提出的方法论：核心思想与关键技术细节
### 2.1 核心思想
- 通过**证据配对**（requirement semantics ↔ repository architecture evidence）构建每条子需求对应的可靠功能链。
- 将每条功能链编译为**互补的双可执行规范**：
  - **架构规范**：检查功能链结构的完整性（单元存在、关系保持、数据流连贯）。
  - **行为规范**：检查功能链在实际运行时的正确性（输出、边界条件、状态转换）。
- 在代码生成过程中，持续执行这两个规范，获得**局部化的反馈**，指导智能体修复，从而长期保持设计-实现一致性。

### 2.2 关键技术细节
1. **证据导向功能链构建**：
   - 输入特征指令 \(I\) 和仓库 \(R\)。
   - 将 \(I\) 分解为子需求集 \(\{r_1, r_2, \dots, r_m\}\)。
   - 对每个 \(r_i\)，识别候选实现单元 \(\{u_1, u_2, \dots, u_n\}\)。
   - 通过**证据驱动推理**建立有序功能链：\(c_i = \{u^1_i, e^1_i, u^2_i, \dots, u^k_i, e^k_i, u^{k+1}_i\}\)，其中每个证据 \(e^j_i\) 同时包含需求语义解释和仓库架构证据（如设计模式、调用关系、依赖等）。

2. **双可执行规范编译**：
   - **架构规范** \(s^{arch}_i\)：使用模板 \(\tau_{arch}\)，包含三类检查：
     - `CheckUnit`：验证所需单元是否存在。
     - `CheckRelation`：检查相邻单元之间的意图关系（如调用、继承）是否保持。
     - `CheckDataFlow`：验证数据流（如传播、序列化）是否通畅。
   - **行为规范** \(s^{beh}_i\)：使用模板 \(\tau_{beh}\)，在多个观察作用域 \(\pi^q_i\) 上检查：
     - `CheckOutput`：可观察输出（返回值、外部效果）。
     - `CheckBoundary`：边界/异常条件。
     - `CheckState`：状态转换。

3. **规范引导的代码生成**（算法1）：
   - 将所有子需求的规范聚合为 \(S_{arch}\) 和 \(S_{beh}\)。
   - 智能体迭代生成代码补丁 \(\Delta P\)，然后在更新后的仓库上执行两个规范。
   - 若任一规范失败，则将局部化反馈（缺失单元、断开的调用、错误输出等）提供给智能体用于下一轮修改。
   - 持续迭代直到所有规范通过或达到交互预算 \(K\)。
