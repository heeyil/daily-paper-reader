## Abstract 

Autonomous LLM agents processing mixed-confidentiality data face severe security risks from prompt injection attacks and reason-ing errors. While dynamic Information Flow Control (IFC) provides structural security guarantees, traditional taint tracking perma-nently taints an agent’s context upon reading unvetted data, se-verely restricting downstream utility. We present APPA ( Agentic Permissions Policy Algebra ), an IFC framework that resolves this usability bottleneck through engine-managed context branch-ing and prospective acquisition enforcement. Before data acquisi-tion occurs, APPA prospectively evaluates label descents and miss-ing prerequisites, generating actionable remedy plans ( Authorize ,

Accept ). To inspect unvetted data without polluting the primary context, a label-seeded child trajectory is spawned, absorbing label descent locally and allowing a trusted sanitizer to return a bounded derivative to the unchanged parent. Governed by a two-monoid model over security labels and shared event logs, we formally prove parent label preservation and merge confinement. Finally, we eval-uate APPA on a multi-turn tool-chaining benchmark across four models: it suppresses exfiltration (31%–50% down to 0%–7% attack success), and on three of the four, branching recovers a substantial share of the utility that taint tracking alone forfeits.

## 1 Introduction 

Delegating tasks to an LLM agent introduces a computational vari-ant of the principal–agent problem [ 21 , 37 ]: the agent acts with the delegated authority of its principal while consuming data and instructions across shared channels. Whenever an agent processes sensitive context alongside unvetted tool outputs, external inputs, or untrusted data, structural risks inevitably arise. Unauthorized data exfiltration, unintended tool calls, and policy violations can re-sult from adversarial prompt injection—where attacker-controlled text hijacks control flow [ 17 ]—but also from model hallucinations, ambiguous instructions, or miscalibrated agent reasoning [ 22 ]. In all these cases, exposing a capable agent to private data, external sinks, and unvetted content turns read access into a vector for exfiltration and policy breaches. Existing defenses generally fall into two main paradigms. On one hand, imperative guardrails—such as hardcoded conditional logic (if statements), prompt-injection classifiers, and output hygiene rules [ 20 , 36 ]—judge content or enforce ad-hoc per-tool conditions. Such guardrails enumerate interactions rather than compose them: every new tool or policy rule requires revisiting ad-hoc conditional logic across the system. Content-judging guardrails are further by-passed by paraphrasing, offer no guarantees against non-adversarial agent errors, and treat prompt injection as an isolated bug rather than a symptom of mixed-confidentiality processing [ 39 ]. On the other hand, static structural restrictions—such as fixed allowlists, rigid role boundaries, or mandatory human-in-the-loop approvals— judge structure . While deterministic, coarse structural restrictions tend to be overeager, severely degrading agent utility and blocking legitimate workflows [28, 45, 47]. Agent Information-Flow Control (IFC) offers a principled third approach by tracking confidentiality and integrity labels across the agent’s tools to track and restrict information flow between given sources and sinks [ 8 , 9]. However, existing agent IFC frameworks face a severe usability bottleneck: label creep . When an agent reads restricted data, dynamic label tracking and taint tracking [ 3, 7 , 42 ]permanently elevate the context’s confidentiality level, revoking access to downstream tools for the remainder of the task and degrad-ing agent utility. APPA ( Agentic Permissions Policy Algebra )resolves this usability bottleneck through twin core mechanisms: 

branching for taint confinement and prospective acquisition enforce-ment with remedy plans .First, APPA operationalizes branching for taint confinement to prevent label creep in the primary execution context. Instead of allowing a sensitive read to permanently pollute the main agent context and lock out downstream tools, APPA isolates sensitive computations within disposable child branches. Operating under narrowed permissions, the child branch inspects data or performs in-termediate reasoning locally; upon exit, only clean sanitized deriva-tives or explicitly accepted returns reach the parent, leaving the primary context unpolluted and fully operational (Figure 1). Second, APPA introduces prospective acquisition enforcement to turn data access blocks into structured, manageable policy events through remedy plans . Rather than silently failing or forcing devel-opers to scatter ad-hoc guardrails throughout agent code, APPA evaluates policy constraints prior to tool execution. ## 2 Related Work 

Table 1 compares APPA with closely related online agent safety, capability, and information-flow control (IFC) frameworks across four key dimensions: the underlying security model, the trajec-tory taint strategy, the operational scope of state tracking, and the mechanism for policy overrides and declassification. 

Closest comparison: Fides and Agent IFC. Fides is the primary an-tecedent for APPA, formalizing dynamic information-flow control (IFC) for agent planners [ 8]. While both share label-based enforce-ment decoupled from the LLM, they differ in mechanics (Table 1). Structural frameworks like ACE [ 27 ] decouple planning into ab-stract and concrete phases for static verification. Fides mitigates label creep by evaluating tool outputs post-execution to hide re-strictive fields in planner variables. In contrast, APPA evaluates acquisitions prospectively before data enters the trajectory, isolat-ing sensitive sub-computations in disposable child branches and handling exceptions via single-call atomic rulings. By validating au-thority before execution, APPA prevents untrusted payloads from polluting the main planner context and triggering irreversible taint accumulation. 

Semantic, memory, and provenance systems. Frameworks address distinct scopes across the agent lifecycle. MemLineage [ 34 ] gates actions on signed memory entry derivation graphs across sessions. In contrast, APPA’s trajectory labels and append-only event log govern single runs, enabling MemLineage to provide persistent provenance at APPA’s boundary. Offline tools like NeuroTaint [ 6]perform post-hoc causal analysis across sessions, complementing APPA’s online enforcement. Execution provenance taxonomies [ 46 ]model typed graphs to trace semantic dependencies between inputs and output claims. In contrast, APPA’s event log records only oper-ational tool actions and rulings, enforcing policy without tracking semantic claim attribution. 

Process isolation vs. trajectory branching. Container and browser sandboxes — such as DeltaBox [14], Crab [49], and ceLLMate [29] — provide OS-level checkpoint/restore and authority sandboxing, carrying classical OS dynamic IFC (Flume [ 24 ], HiStar [ 51 ]) and floating-label IFC (LIO [ 43 ]) into the agent setting. APPA operates orthogonally: while system sandboxes snapshot OS processes and filesystems, APPA confines label propagation at the LLM context trajectory layer, isolating unvetted tool data within child branches without memory rollback or hardware enclaves. Consequently, APPA can operate alongside process sandboxes to provide defense-in-depth across both OS environment and prompt context bound-aries. 

Guardrails and structural isolation. Imperative guardrails — such as NeMo Guardrails [ 36 ], boundary sanitizers [ 4], and Llama Guard [ 20 ] — filter content without lineage tracking, leaving them vulnerable to paraphrasing or context drift. Structural patterns like Dual LLMs [ 48 ] and CaMeL [ 9] enforce isolation but require restructuring harnesses into multi-role architectures, while capability-safe harnesses like TACIT [ 33 ] enforce static capabilities via code synthesis. In contrast, APPA operates dynamically at the tool-dispatch layer of standard harnesses via pre-dispatch hooks.

Integrating external policy logic through log views. Custom exe-cution policies and numerical thresholds are implemented via log projections coupled with external authority resolvers. For example, cumulative metrics such as financial spend limits ( finance.spend )are computed by log views that determine whether an action re-quires human authorization. Recording these operations as named log events avoids introducing quantitative state into the label alge-bra, keeping scalar magnitudes outside the lattice model.

Unknown. Unknown values are not represented as elements within the lattice carrier; there is no ordering such as trusted <

unknown < suspicious . Unresolved attributes remain outside the label algebra, preserving total algebraic composition and monoid laws while policy checks detect missing information. Reclassifying unknown inputs requires explicit, audited cast events. A cast is defined either as a static constant or via a dynamic resolver re-stricted to a bounded set of admissible target labels. Static casts establish a fixed default policy, while target ceilings prevent dy-namic classifiers from arbitrarily elevating un-trusted data. This treatment aligns with gradual typing interpretations of unknown values [ 13 , 15 ], directly mirroring how static type checkers manage partially annotated Python or TypeScript codebases: unannotated inputs default to an unclassified Unknown boundary rather than an assumed default position in the type hierarchy, requiring explicit casts or assertions to enter the security algebra.

If a result value is admitted, its Label enters the fold; otherwise, the Label is unchanged. Trajectory branching is deliberately excluded from the mecha-nisms that clear an acquisition block. Because a child trajectory is seeded from the parent’s current label state 𝑠 parent , it inherits the same initial restrictions; context branching serves as an engine-level orchestration option to isolate execution under inherited labels (§6) rather than clearing parent restrictions. Clearing an acquisition block within any active trajectory strictly requires explicit agent acceptance. The two verification steps remain decoupled: an exter-nal policy ruling cannot accept state narrowing on behalf of the agent, and agent acceptance cannot satisfy an unmet tool require-ment. Because release-side requirements (trust floor and audience cover) are monotone in the trajectory label 𝑠 , state descent can only shrink the set of tool requests satisfiable without explicit rulings. Conversely, upper context bounds (such as source bounds ⊆ 𝐶 )are antimonotone: narrowing permissions can cause a previously failing upper bound to become satisfied, which excludes them from the monotone scope of Call-Scoped Release (Theorem 5.1).

Remedy-plan delivery. The planner distinguishes atomic exe-cutable plans from prose or advisory recommendations. Executable plans— Authorize (issuing policy rulings), Accept (accepting state narrowing), or single-call compositions combining both—are ex-ecutable objects exposed through a static tool, execute_remedy_ plan(plan_id), initialized at run start to avoid invalidating prompt caches [ 25 ]. The plan identifier, tool dispatch, and associated policy rulings are logged upon execution. Unmet hard gates use the same interface: a hard gate is treated as a failed predicate requiring an atomic ruling. By contrast, Redispatch recommendations are non-atomic: they propose two or more separately checked calls (e.g., registered tools whose successful effects satisfy a failed prior(k) requirement or whose restrictive deltas cure an audience cap). Redispatched calls are ordinary tool calls checked and executed independently, after which the original target call must be reproposed and rechecked. Advisory Branch recommendations suggest context isolation with-out directly satisfying unmet tool requirements. 

## 5 Atomic Rulings and Robust Declassification 

One judgment and one dispatch rule. Every judgment follows a single canonical form: authority 𝐴 authorizes engine-rendered call 

𝐶 . System vocabulary consists exclusively of mandates, rulings, and log records. A call is dispatched if and only if: (1) rulings cover all failed or demanded predicates, (2) each issuing authority’s mandate permits the exception, and (3) all rulings target the identical ren-dered call and are consumed atomically. Multi-party authorization policies (such as two-person control [ 41 ]) collect multiple rulings for one call. A ruling permits dispatch despite an unsatisfied predi-cate but never modifies the execution trajectory directly; instead, tool return values update the trajectory Label via standard accumu-lation (§3), and successful dispatches record declared side effects in the event log E. No ruling bypasses the explicit agent acceptance required for narrowing (§4). 

Atomic plan execution. For a plan requiring authorization on a blocked step, an indivisible operation renders the call, presents provenance to the authority, and dispatches upon approval. Plan identifier, ruling, and dispatch event are recorded atomically in the event log. Approval and dispatch coincide, collapsing multi-stage grant lifecycles (issuing, binding, consuming) [ 30 ] into an atomic step that prevents call substitution, replay attacks [ 32 ], and intermediate interception [44]. 

Call-scoped release. A ruling applies strictly to a single dispatch without altering the trajectory label. Single-command scope iso-lation ensures an authorized exception cannot persistently relax labels for subsequent attacker-influenced calls [41].

Mandate typology. Authority is bound to declarative mandates: (1) Cover mandates (permitting trust gaps or audience ceilings), (2) Named waivers (exempting history predicates), and (3) Gate mandates (satisfying hard gates). A single ruling may address both an unmet predicate and a hard gate, but cannot bypass narrowing acceptance. Misrouted checks evaluate against the exact rendered call. 

Response-sink rule. No primary user ruling can authorize a pred-icate for a direct user response sink, irrespective of mandate privi-leges, preventing in-band self-approval vulnerabilities [41]. 

Canonical rulings and robust release. Authorities evaluate the en-gine’s canonical representation of a tool call, eliminating semantic evasion vectors where a compromised model requests actions under misleading phrasing. Following established declassification mod-els, sanitization regulates what information is released, whereas rulings govern who permits release [ 40 , 50 ], establishing robust declassification over exact rendered calls. 

Sanitizers. Registered sanitizers transform values according to authorized state transitions without altering execution trajecto-ries [ 4, 6]. Sanitization adjusts audience scope exclusively and never elevates trust levels without an explicit ruling, cast, or exit trans-formation (§6). 

User-assistant trust boundary. The root response is modeled as a sink whose recipient set is the authenticated root principal, and is adequate exactly when the current trajectory Label covers that principal. Mediating that sink is out of scope in this version; only the structural bar above is enforced. External outbound commu-nications remain encapsulated within tool calls subject to policy validation. 

## 6 Branching for Taint Confinement 

By delegating restrictive data acquisitions to disposable child branches, APPA isolates label descents locally, preserving the parent trajectory’s permissions without claiming the child itself is untainted [ 6]. This adapts dynamic sub-computation confinement from floating-label systems like LIO [ 43 ] to LLM agent transcript branching with post-branch isolation. Context branching requires an engine execution environment capable of isolating context trajectories (e.g., an application harness or proxy gateway). While baseline label enforcement (§4) operates in standard protocol gateways (e.g., MCP [ 2], SMCP [ 18 ], MCPShield [ 53 ]), engine-managed context branching and output sanitization rely on runtime confinement. 

Engine branching protocol. Branching is orchestration: a narrow-ing check blocks the original call, the planner may only recom-mend a branch (advisory, never a plan step), and the harness—not the APPA policy state machine—creates the child, on an agent fork request or by deterministic orchestration. APPA then mod-els branching as an engine-managed protocol surrounding engine enforcement: (1) the harness requests a child context; (2) the engine identifies the active parent trajectory; (3) the APPA engine records a branch boundary and seeds the child from the parent’s current label; (4) the engine submits child-local work; (5) the child’s calls are evaluated independently; and (6) any returned value crosses through the checked child-return and parent merge path.

The branch boundary also invalidates pending rulings and plan executions, as these records are bound to specific parent invocations and cannot transfer to a child. Snapshot inheritance preserves conversational continuity and reduces task-framing overhead. Because the child shares an exact token prefix with the parent up to the branch boundary, pre-branch snapshot inheritance is inherently prompt-cache friendly [ 25 , 52 ]: inference engines can reuse pre-computed Key-Value (KV) cache states, avoiding the prompt re-synthesis and token duplication required when instantiating isolated verifiers in Dual-LLM or multi-agent architectures [ 9 , 48 ]. The confinement boundary is directional: new child-local context cannot enter the parent transcript before an explicit, checked exit. The engine must still provide the child-local work instruction, while inherited context need not be reconstructed in that instruction. 

Child-local execution. Child-local work is dispatched within the child context, where all subsequent actions are enforced against the evolving child label 𝐿 𝑐 . Updates to 𝐿 𝑐 affect only the child label and never update 𝐿 𝑝 . The parent process remains isolated from post-branch child messages and tool outputs until an explicit exit occurs, guaranteeing the pre-merge properties of Theorem 6.1 regardless of child behavior. 

Explicit branch exit. An execution branch yields three outcomes: APPA 

(1) an abandon signal; (2) the return of a standard labeled value; or (3) the application of a registered sanitizer or verified exit trans-formation that produces a derived value. In all cases, APPA validates the actual result label prior to com-mitting the merge. If the raw result would restrict permissions, it triggers the acquisition check in the parent context. The parent may explicitly accept the label reduction or reject the merge ; however, accepting lower permissions does not achieve taint confinement. A declared exit bound can be verified prior to execution to enable planning, though the actual result label remains authoritative.

Shared event log. The parent and child trajectory append to a single, real-time serialized event log. Any effect committed by a successfully closed child dispatch remains visible tree-wide across all branches after abandonment; context isolation cannot undo these actions nor clear them from future no_prior(egress) policy checks [ 46 ]. A successful child egress therefore affects a parent’s 

no_prior(egress) check, whereas a failed or indeterminate child dispatch does not add committed effects to the shared projection. Branch creation and merging function as governance operations. A policy ruling granted to a child is consumed during its execution and does not grant authorization to the parent. Each branch terminates via return, failure, or abandonment, requiring no log reconciliation because the event log is never branched. 

Sanitized branch exits. Following the Dual-LLM and CaMeL ar-chitectures [ 9 , 48 ], sanitized branch exits pair a predeclared submit_ result schema with registered transformation functions. Schema validation alone never relaxes label restrictions, as structural com-pliance does not guarantee safe provenance [ 39 ]. Maintaining a parent process’s trust level may require a verified transformation assertion [ 50 ]—for example, asserting that “the returned integer represents a version number from the specified source and con-tains no unparsed text”—rather than simple parsing. Registering such a transformation incorporates its claim into the trusted com-puting base; this transformation assertion represents APPA’s sole exception for structured label promotion without an explicit ruling. 

## 7 Evaluation 

To evaluate dynamic information flow control and context branch-ing, we developed bench-corp, a controlled corporate-assistant benchmark for probing enforcement behavior across multi-step, multi-tool trajectories. Existing agent security benchmarks, such as AgentDojo [ 10 ], InjecAgent [ 11 ], and ToolEmu [ 38 ], evaluate prompt injection primarily over single-step tasks or short detection horizons. Such benchmarks do not isolate the core trade-offs of dy-namic IFC: cumulative Label descent and downstream loss of utility manifest specifically in multi-step workflows, where an early re-strictive read disables subsequent tool dispatches. We instrumented AgentDojo (all four suites, tool_knowledge attack) and found two structural reasons why it cannot discriminate context branching. First, the attack no longer lands on a current-generation model: GPT-5.6 Luna never complied across 160 undefended workspace episodes, nor across a 60-episode probe of five further attack fami-lies, whereas GPT-4o complied in 31% of its undefended episodes. A defense evaluated against this attack therefore scores 0% whether or not it does anything. Second, its tasks are read-then-act with a sin-gle goal: no later independent benign action depends on the parent Label, so preserving it changes no outcome, and observed branch usage differs by an order of magnitude between models on the same tasks. Enforcement costs utility on these tasks: 47% against 77% for the same loop under a null policy on GPT-4o, and 67% against 88% on GPT-5.6 Luna. Of the 32 GPT-4o tasks that pass under the null policy but fail under enforcement, 8 are policy blocks and 24 are mediation overhead in our harness. bench-corp is structured as a suite of target mechanism probes isolating cumulative Label descent, downstream utility retention, recipient-sensitive policy enforcement, and trajectory-local context branching. 

Environment and tool surface. Every episode operates on a mock company environment exposing six systems: five CRUD stores—hr (confidential employee records), finance (invoices and financial records), task_tracker (internal tickets and audit notes), public_forum (untrusted external inputs), and vendor (supplier records, contracts, and onboarding documents)—plus email (outbound egress sink). The environment exposes seventeen tools: search, read, and create for each of the five CRUD data stores, plus send_email and composite action share_legal_packet. Each scenario selectively enables only the subsystems necessary for its task; the agent sees a correspondingly reduced tool surface, and APPA prunes its enforced policy to match. All tool executions produce observable filesystem state: emails write to an outbound sink file, and internal operations mutate sub-system data directories. An episode runner initializes each run by copying pristine scenario data into a fresh directory with an empty sink, guaranteeing zero shared state across episodes. Complete task prompts are provided in Appendix B. 

Scenario taxonomy and branching dynamics. The fourteen sce-narios in bench-corp reflect distinct structural dependencies: under APPA’s policy, three scenarios are structurally branch-dependent 

(unwinnable without context branching)—reply-and-file-ticket, email-onboarding-buddy, and review-then-notify. Six of the four-teen tasks are native-expressiveness scenarios designed to isolate policy distinctions represented directly by a defense’s native state model: joint-merger-brief (audience intersection vs. ordinal confi-dentiality ceilings), one-release-only (one-shot history predicates vs. folded context labels), public-directory-card (transformer out-put redaction), vendor-trust-boundary (intermediate trust ranks vs. binary integrity), share-legal-packet (pre-dispatch vs. post-effect Arseny Kravchenko, Vadim Liventsev, Innokentii Konstantinov, Ildar Iskhakov, and Matvey Kukuy 

labeling), and review-then-notify (side-effect notification with-out context leak). In three restrictive-read tasks (check-hr-record, inspect-forum-post, and check-forum-and-hr), an agent can avoid Label creep by executing independent routine actions before in-specting restrictive data. Five scenarios embed indirect prompt injections in public forum content; hide-secret-in-status tests data-field smuggling; check-hr-record and email-onboarding-buddy evaluate accidental over-disclosure risks without adversarial injec-tion. 

Experimental arms and harness controls. The evaluation com-pares five implemented experimental arms: (1) APPA: Guarded APPA policy enforcement with fork and submit_result primitives enabled. (2) APPA-no-fork: The identical APPA binary and policy ex-ecuted with --max-forks 0 .(3) APPA-open: The APPA agent loop executing under a neu-tral baseline policy. (4) Fides : Microsoft Agent Framework enforcing Fides pol-icy with automatic untrusted content hiding and tool-less quarantine [8]. (5) Fides -open: The Microsoft Agent Framework loop exe-cuted without SecureAgentConfig. The open arms serve as harness-matched controls for their respec-tive runtimes: APPA executes Rust corporate systems in-process, whereas Fides accesses systems over MCP. The baseline compari-son also incorporates expressiveness asymmetries: APPA enforces value-granular recipient policies on finance data, whereas Fides 

relies on an ordinal confidentiality floor; scenario-specific APPA policy rules (such as reply-and-file-ticket requiring prior egress before filing tickets) rely on dynamic history predicates, whereas 

Fides applies static policy attributes (e.g., blocking untrusted create_ task_tracker calls via accepts_untrusted =False and capping create_ public_forum confidentiality). 

Execution protocol and declarative scoring. An automated runner executes each episode as an isolated subprocess, supplying sce-nario prompts and capturing stdout, stderr, and residual filesystem state upon exit. Scenarios are evaluated against declarative end-state predicates rather than an LLM judge. Scoring applies four case-insensitive string-matching predicate types: matching email presence, email absence, required or forbidden substrings in created files, and required or forbidden content in printed answers. For utility-bearing tasks, an episode succeeds only if all utility predicates pass (evaluated across thirteen utility-bearing scenarios). For security evaluation, an episode is marked as breached if any 

security predicate passes (evaluated across all fourteen scenarios). Residual state is scored even after timeouts or abnormal process termination, ensuring early egresses are correctly registered as attack successes. Diagnostic event counts (policy blocks, remedy invocations) provide log trace visibility without altering utility or security scores. Across the three repetitions, per-arm results varied by at most three episodes.

## 8 Limitations and Future Agenda 

Scope of claims and TCB boundary. The formal guarantees of APPA operate within explicit boundary conditions on the threat model and TCB. First, although the model is policy-untrusted, covert timing channels from an actively malicious model [ 19 ] re-main out of scope. Second, enforcement relies on declared contract labels and registered derivation functions; sanitizer correctness re-sides within the TCB [ 42 ], and an undeclared write-side contract ad-mits a store-mediated laundering path (§7); requiring store-writing tools to declare sink requirements rules out the undeclared case. Third, context branching enforces trajectory isolation rather than transactional side-effect rollback [ 46 ]; external network egresses committed by a child branch before discard cannot be reverted. 

Empirical bounds and future evaluation agenda. The bench-corp benchmark suite provides tight causal isolation for mechanism probing over a controlled tool surface. However, establishing opera-tional effectiveness across production enterprise workloads requires further research: (1) evaluating real-world task ambiguity and di-verse organizational policies; (2) testing multi-model generalization across model families and prompting strategies; (3) quantifying long-horizon behavior and resource overheads (latency, token con-sumption); and (4) measuring human approval fatigue [ 1 ] and policy authoring ergonomics in realistic deployment settings. 

## 9 Conclusion 

Traditional information flow control prevents data leaks, but dy-namic tracking mechanisms create a severe usability bottleneck by permanently restricting context after sensitive operations [ 8 ]. APPA resolves this bottleneck through a structural branch lifecycle: 

• evaluating data acquisitions prior to dispatch, 

• isolating restrictive reads in disposable child branches, and 

• merging policy-compliant results into the parent trajectory. By bounding label scope and maintaining a unified event log across execution paths, APPA keeps the parent context clean without relying on ad-hoc sanitization or prompt-level mitigations [ 9, 48 ]. Ultimately, APPA demonstrates how agent engines can enforce rigorous security policies while preserving context continuity.

Proof of Theorem 5.1 (Call-scoped release). (i) By the dispatch rule, a call with requirement gaps dispatches only through atomic plan execution: one indivisible step renders the call, obtains a covering ruling for each gap over that rendered call, records the acceptance of any narrowing, and dispatches. Each ruling is created and consumed within this step, so no reachable log contains a free-standing ruling, and no ruling is consumed by a second dispatch. Gaps with no covering mandate ( prior , caps) cannot be present at any dispatch: a call carrying them dispatches only after redispatch remedies cure them and a re-check finds them absent. (ii) By induction on the log: among all event kinds, only value admissions, merges, and audited cast resolutions update a trajectory Label—admissions and merges are meets (§3), and a cast only estab-lishes an Unknown dimension, never rewrites an established one— and only committed effects ( DispatchSucceeded or CloseSuccess )extend E. A ruling or acceptance event is a record, the identity on every trajectory Label and on E. The ruled dispatch’s consequences Arseny Kravchenko, Vadim Liventsev, Innokentii Konstantinov, Ildar Iskhakov, and Matvey Kukuy 

enter only through those ordinary channels: its admitted value’s Label folds restrictively, and emits commit on reported success. (iii) By (i), every dispatch with an unmet release-side Label re-quirement consumes at least one ruling, and no ruling is shared between dispatches, so in any trajectory such releases are matched to the explicit rulings in the log: no unruled inadequate release exists. By (ii) and Proposition 3.2, the Label after a ruled dispatch is at most the Label before it, so the same resolved release-side requirement—a trust floor, or an includes over the same resolved recipient set—that failed before the override still fails after it (both are monotone in the Label; a later rendered call whose placeholders resolve differently presents a different requirement, checked afresh). A cap or a prior predicate may newly pass after the override, but not through the ruling: the reader set only shrank by the trajec-tory’s own restrictive descent, and the effect is one the ruled call was itself authorized to commit. An override therefore widens no later Label and confers no authorization on any other dispatch: each subsequent inadequate release presents its own gaps and, by (i), consumes its own rulings.
