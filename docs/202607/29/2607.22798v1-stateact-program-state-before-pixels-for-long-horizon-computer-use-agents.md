## 摘要
计算机使用代理通常通过强化感知来改进：更好的模型用于读取截图并选择点击位置。然而，截图只是底层程序状态的有损渲染，例如保存任务数据的文件、应用程序后端和DOM。不同的状态可以产生相同的像素，而代码可以直接检查和修改该状态。StateAct是一个基于这一区别的代码优先、多代理框架。其主要代理通过使用代码直接与程序状态交互，而专门的GUI子代理负责处理需要截屏和点击的少数子目标，在108个任务中仅有28个需要，占主代理步骤的1.1%。对程序状态的直接访问也支持验证：一个独立的完成门会双重检查保存的结果是否存在结构性失败，例如输出缺失、未保存或写入错误路径。为了在数百个步骤中保持正确方向，主代理将子目标交给新的子代理，保持其自身的上下文聚焦。在OSWorld 2.0上，StateAct将Claude Opus的二元成功率从20.6%提升至26.9%，部分成功率从54.8%提升至61.6%，每个任务的成本约为仅使用截图的同一模型的九分之一；没有GUI子代理的纯代码变体仅达到45.9%的部分成功率，低于基于截图的基线54.8%。总的来说，将动作、验证和记忆基于状态（我们称之为状态基础化）将主要瓶颈从感知转向推理：失败更多地取决于代理的思考而非所见。

## Abstract
Computer-use agents are usually improved by strengthening perception: better models for reading a screenshot and choosing where to click. Yet a screenshot is only a lossy rendering of the underlying program state, e.g., the files, application backends, and DOM that hold the task data. Different states can produce the same pixels, while code can inspect and modify that state directly. StateAct is a code-first, multi-agent harness built around this distinction. Its main agent works directly with program state by using code, while a dedicated GUI subagent handles screenshot-and-click interaction on the few subgoals that need it, just 28 of 108 tasks and 1.1% of main-agent steps. The same direct access to program state also supports verification: an independent finish gate double-checks the saved result for structural failures, e.g., output that is missing, unsaved, or written to the wrong path. To stay on track over hundreds of steps, the main agent hands subgoals to fresh subagents, keeping its own context focused. On OSWorld 2.0, StateAct lifts Claude Opus 4.8 from 20.6% to 26.9% on binary success, and from 54.8% to 61.6% on partial success, at ~ 9x lower cost per task than the same model driven by screenshots alone; a code-only variant with no GUI subagent reaches only 45.9% partial, below that screenshot-based baseline's 54.8%. In general, grounding action, verification, and memory in state, what we call state-grounding, shifts the main bottleneck from perception toward reasoning: failures depend more on what the agent thinks than on what it sees.

## 2. 方法论：核心思想、关键技术细节

- **核心思想**：主代理（main agent）通过代码（bash、Python、文件编辑器）直接读写程序状态，仅在必要时（1.1%主代理步骤，覆盖28/108任务）通过专用GUI子代理（GUI subagent）使用截图点击。同时构建独立完成门（finish gate）验证持久化结果，并通过上下文管理支持数百步执行。
- **关键技术细节**：
  - **状态优先行动**：主代理动作空间包括bash、Python、文件编辑器、只读图像查看器、计划清单、完成动作和代理委托工具。无实时屏幕控制（鼠标/键盘）。状态发现通过模型先验和主动探测定位程序状态存储位置。
  - **委托规则**：当子目标不可通过代码寻址（无文件/后端/DOM路径，或仅能通过渲染交互表达）时，主代理委托给GUI子代理；浏览器工作由专用web子代理通过CSS选择器、DOM序列化等结构化方式处理。
  - **完成门**：独立于主代理的第三方验证，仅接收任务指令和机器访问（bash、文件读取、DOM查询），拒绝读取主代理的消息历史、计划或完成理由。四特性：叙述盲、状态接地、反捕获、有限纠正（最多三轮重试）。
  - **上下文管理**：新鲜上下文子代理（每个委托运行在独立窗口，返回简洁报告）、自动压缩（接近上下文限制时摘要旧前缀并移除图像）、外部化计划（持久化在历史外，每次重新注入）。
- **算法流程（文字说明）**：主代理循环执行动作（代码或委托）→ 当调用finish时触发完成门 → 完成门独立检查持久化工件 → 通过则结束，拒绝则返回主代理修复（最多3轮）。仅当主代理至少执行3个非finish步骤后才允许调用finish。

## 6. 主要结论与发现

- StateAct在OSWorld 2.0上将Claude Opus 4.8的二元成功率从20.6%提升至26.9%，部分成功率从54.8%提升至61.6%，成本降低约9倍（$7.8 vs $72）。
- 增益主要来自状态基础化的行动（去除后部分成功率降至51.3%，低于基线54.8%），而非增加代理深度（递归仅触发7/108任务）。
- 瓶颈从感知转向推理：79个非完美任务中38个源于推理错误，14个由完成门错误通过，22个涉及模态瓶颈或指令歧义。完成门检测结构缺陷（8个正确拒绝）但无法验证值正确性（68/76错误通过）。
- 紧凑GUI子代理在短程或移动基准上足够，但长程桌面任务（OSWorld 2.0）仍需强大GUI模型（SFR-CUA变体部分成功仅43.2%）。

## 7. 优点

- **创新架构**：代码优先、多代理、状态基础化的设计有效利用程序状态，克服截图有损渲染的固有限制。
- **显著性能提升**：在相同模型上实现更高准确率且大幅降低成本，结果超过所有公开前沿系统。
- **分析深入**：完成门特性、失败根因、瓶颈转移诊断清晰，提供了对Agent设计的重要洞察。
- **实验覆盖广**：多个基准、消融、子代理替换、不同骨干验证，增强了结论的稳健性。
- **实用意义**：低成本、高精度，可直接部署于现有长程桌面任务系统。

## 8. 不足与局限

- **完成门局限**：仅能检查结构错误（缺失文件、错误路径、格式不匹配），无法验证值正确性（68/76错误通过）。这导致部分成功率与二元成功率之间有较大差距（61.6% vs 26.9%）。
- **仅为推理框架**：未涉及模型训练或微调，基于已有语言模型（Claude Opus 4.8），增益可能通过进一步适配更大化。
- **骨干依赖性**：主实验仅使用同一模型（Claude Opus 4.8），对其他骨干（如更弱或开源模型）的适用性仅做初步验证（Sonnet 4.6增益较小）。
- **任务类型限制**：对纯视觉任务（图像编辑、布局、图表外观等）无优势，其效果依赖任务是否状态可寻址（state-addressable）。系统概念上对渲染专属任务可为零增益。
- **长程桌面任务仍需强大GUI子代理**：在OSWorld 2.0上替换为紧凑模型SFR-CUA后性能大幅下降，提示在某些困难场景下视觉能力仍是必要。
- **算力与复现**：文中未提供GPU配置、训练成本等细节，可能影响完全复现。成本估计基于推理调用次数和API价格，实际部署可能因提供商而异。
