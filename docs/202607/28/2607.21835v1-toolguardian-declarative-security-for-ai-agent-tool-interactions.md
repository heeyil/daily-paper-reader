## 摘要
LLM智能体越来越依赖外部工具，这扩展了能力，同时创造了新的安全边界：第三方工具可能在接口层面看似良性，但在实现中嵌入不安全行为。现有防御依赖于弱元数据，将特征描述和策略判断合并为单一决策，或使用启发式/LLM执行，缺乏对任务上下文和多工具组合的确定性、可审计推理。本文提出ToolGuardian，一个策略驱动框架，通过准入审查和任务感知的运行时授权来保护智能体与工具交互。ToolGuardian使用渐进式特征描述将证据转换为结构化事实：描述捕获声明的意图，系统调用轨迹暴露粗略行为，模拟执行揭示观察到的效果，源码分析识别潜在行为。ToolGuardian的核心贡献是一个基于答案集编程（ASP）的声明式策略层，它能显式推理能力、效果、任务上下文和组合。我们使用相同的输入和输出契约，将ASP与启发式和基于LLM的策略实现进行比较。我们在16个MCP风格的工具上评估ToolGuardian，包括8个来源于真实开源工具的恶意变体，以及20个运行时场景。对于审查，使用描述、系统调用和观察效果证据，ASP达到了0.86的拒绝类F1分数和88%的准确率。对于运行时授权，完全指定的实现正确分类所有场景，而消融实验表明，移除组合和一致性规则会大幅降低性能。

## Abstract
LLM agents increasingly rely on external tools, expanding capability while creating a new security boundary: third-party tools may appear benign at the interface level while embedding unsafe behavior in implementation. Existing defenses rely on weak metadata, collapse characterization and policy judgment into a single decision, or use heuristic/LLM enforcement that lacks deterministic, auditable reasoning over task context and multi-tool composition.   This paper presents ToolGuardian, a policy-driven framework for securing agent-tool interactions through pre-admission vetting and task-aware runtime authorization. ToolGuardian uses progressive characterization to convert evidence into structured facts: descriptions capture declared intent, system-call traces expose coarse behavior, mock execution reveals observed effects, and source analysis identifies latent behavior. ToolGuardian's core contribution is an Answer Set Programming (ASP)-based declarative policy layer that reasons explicitly over capabilities, effects, task context, and composition. We compare ASP against heuristic and LLM-based policy realizations using identical inputs and output contracts.   We evaluate ToolGuardian on 16 MCP-style tools, including 8 malicious variants derived from real open-source tools, and 20 runtime scenarios. For vetting, ASP reaches a deny-class F1 of 0.86 and 88% accuracy using description, syscall, and observed-effect evidence. For runtime authorization, fully specified realizations classify all scenarios correctly, while ablations show that removing compositional and conformance rules substantially degrades performance.

  - 使用启发式或 LLM 进行执行决策，缺乏确定性、可审计的推理能力，尤其难以处理任务上下文和多工具组合场景。

- **整体含义**：需要一种分离特征提取与策略执行的框架，支持预准入审查（vetting）和任务感知的运行时授权（runtime authorization），并能显式推理能力、效果、任务上下文和工具组合带来的安全风险。

## 2. 论文提出的方法论

### 核心思想
ToolGuardian 是一个策略驱动的安全框架，将工具特征提取与策略执行分离，通过渐进式表征将异构证据转化为结构化事实，再交由声明式策略层进行推理。

### 关键技术细节

- **渐进式表征**：共四个证据层级，每一层提供更丰富的安全证据：
  - **L0：描述级**：从工具描述、元数据中提取声明意图（但视为不可信）。
  - **L1：系统调用级**：通过系统调用跟踪暴露粗粒度能力（文件读写、网络访问、进程执行）。
  - **L2：模拟执行与观察效果**：在受控环境中执行工具，记录实际效果（HTTP 请求、数据访问、状态修改），但存在覆盖局限。
  - **L3：静态源码分析**：通过 AST 分析识别潜在、条件性行为（如未执行的代码路径），可能过度估计。
  - 累积形成表征层级 P0~P3：P0 = L0, P1 = P0 ∪ L1, P2 = P1 ∪ L2, P3 = P2 ∪ L3。

- **事实表示**：将表征结果统一转化为结构化事实，例如：
  - capability(tool, network_access)
  - data_access(tool, env_vars)
  - observed_effect(tool, http_post)
  - effect_mismatch(tool, undeclared_network)

- **策略实现**：支持三种策略实现，使用相同的输入（结构化事实）和输出契约（决策 + 解释标签）：
  - **ASP 实现**：使用 Answer Set Programming（Clingo 求解器）编写声明式规则，显式编码拒绝条件、例外、效果一致性、组合约束等。提供确定性、可审计的推理。
  - **Heuristic 实现**：基于风险分数、阈值和手写授权逻辑的指令式基线。
  - **LLM 实现**：使用推理型大模型（openai/gpt-oss-120b）通过提示解释结构化事实和策略指令，输出决策。易调整但非确定性。

- **两个执行阶段**：
  - **预准入审查**：在与任务无关的情况下决定是否允许工具进入生态系统。输出：拒绝、受限允许、警告、无限制允许。
  - **运行时授权**：在具体任务上下文中判断单次调用是否允许，考虑能力/效果授权、声明-效果一致性、多工具组合风险（如敏感数据读取后跟网络外发）。

## 6. 论文的主要结论与发现

1. **结构化表征提升可见性但非单调**：P2 层级（添加模拟执行效果）达到最佳审查效果（ASP F1=0.86，准确率 88%）。P3 层级（加入静态分析）虽然暴露更多恶意行为，但也导致对高权限良性工具的误拒绝增加，表明存在安全-效用权衡。

2. **运行时授权在完全指定策略下所有实现均表现完美**：ASP、Heuristic、LLM 均正确分类全部 20 个场景。但消融实验显示：

   - 移除 Heuristic 中的组合推理后，组合场景全部漏报，准确率降至 80%；进一步简化后降至 60%。
   - 说明 **结构化事实本身不足，显式策略结构（特别是组合与合规规则）至关重要**。

3. **ASP 提供确定性、可审计的执行**，但需要专家编写规则；Heuristic 工程直观但不易扩展；LLM 灵活但依赖明确指导且在零散证据下表现差（P0 时从不输出硬拒绝）。

4. **预准入审查与运行时授权是互补的**：工具在审查中可能被限制而非拒绝，从而保留效用，运行时再根据任务上下文细粒度控制。

5. **组合风险是运行时最难的案例**：原子授权相对容易，而多步骤组合（如敏感读+网络写）只有显式组合规则才能阻止。
